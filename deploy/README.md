# Deployment Stack (ETH / BSC / POLY)

The production-shaped deployment of the extractor for the three baseline
mainnet circuits. It is the production version of the demo environment
of `e03/demo`: the same idea — a live NATS pipeline you can watch — but
built on the real contracts: strict per-network YAML, immutable
DestinationBinding descriptors, per-account NATS credentials, streams
carrying the D77 identity metadata, mutual TLS on the ingest boundary
and durable WAL spools that survive every outage.

This stack is the E06-13 deployment pre-build (#71) and the E06-09 live
start pre-build (#69). The adapter and gateway services are mocks: the
real native clients with embedded adapters and the real gateway binary
land with the E01/E06 builds. Every identity, route, permission and
delivery rule is the contract behavior; only the record payloads are
small JSON documents instead of codec fragments, and the ingest wire is
a length-prefixed JSON protocol instead of the pinned gRPC control wire
(`cmd/mock-adapter`, `cmd/mock-gateway`, `internal/wire`).

## What runs

| Service | Circuit | Owns (writable volume) |
|---|---|---|
| `nats` (nats:2.15.1-alpine, JetStream) | transport | `extractor-nats-jetstream` |
| `eth-gateway`, `bsc-gateway`, `polygon-gateway` | one per network, on the circuit and transport networks | `extractor-<net>-journal` |
| `eth-adapter`, `bsc-adapter`, `polygon-adapter` | one per circuit | `extractor-<net>-wal` |

Seven services, seven writable volumes. The full production topology of
NODE_DEPLOYMENT_SPEC is 11 services and 14 volumes: each mock adapter
stands in for one native client (Geth, BSC, Bor plus Heimdall and the
Polygon L1 pair) with its embedded adapter and native datadir volume.

Network topology per NETWORK_PORTS: one bridge network per circuit
(`extractor-eth-circuit`, `extractor-bsc-circuit`,
`extractor-polygon-circuit`), one transport network
(`extractor-transport`) shared by the gateways and NATS. Only two
loopback-bound diagnostic ports are published: the NATS client port on
`127.0.0.1:14222` and the NATS monitoring UI on `127.0.0.1:18222`
(override with `DEPLOY_NATS_CLIENT_PORT` / `DEPLOY_NATS_MONITORING_PORT`).
Those defaults coexist with the demo environment, which holds 4222/8222.

## Layout

```
deploy/
  docker-compose.yml        the full stack
  config/<net>/live.yml     strict collector YAML of one network (LIVE_CONFIG_SPEC)
  config/<net>/gateway.yml  strict gateway YAML of one network (LIVE_CONFIG_SPEC)
  config/<net>/binding.json immutable DestinationBinding (CONTROL_WIRE_CONTRACT)
  scripts/bootstrap.sh      bindings, trust material, NATS accounts, streams
  scripts/up.sh             bootstrap + start everything
  scripts/down.sh           graceful stop (volumes kept; --volumes destroys data)
  scripts/verify.sh         end-to-end verification
  scripts/runbook.sh        operator observation and recovery drills
  bootstrap/                host-side Go bootstrap tool
  cmd/ internal/            the mock gateway and mock adapter
  secrets/                  generated by bootstrap, never committed
  .build/                   local build output, never committed
```

## Bring the stack up

Requirements: Docker with Compose, Go 1.26 or newer (for the bootstrap
tool and the image builds).

```bash
cd deploy
./scripts/up.sh
```

`up.sh` runs `bootstrap.sh` first. From a clean checkout the bootstrap:

1. verifies the committed binding descriptors against the repository's
   authoritative `gateway/destination` reader (the deploy tree carries
   its own reader for the self-contained Docker builds; bootstrap
   cross-validates the two on every run);
2. generates the private CA, the NATS server certificate, the gateway
   and adapter certificates with `deploy/<network>/<role>` identities,
   and the NATS account configuration with two users per network account:
   a bootstrap user (stream administration inside its account) and the
   runtime gateway user (publish into `evm.v3.<chain>.>`, ask
   `$JS.API.INFO`, `$JS.API.STREAM.INFO.<stream>` and `$SYS.REQ.USER.INFO`,
   subscribe only to its `_INBOX.>` reply prefix);
3. starts NATS and creates each network's stream with the two D77
   identity keys (`extractor.network_digest`,
   `extractor.destination_id`), `MaxMsgSize` 2097152 and the
   `evm.v3.<chain>.>` subject namespace, then reads the StreamInfo back
   and verifies identity, subjects and limits before reporting success.

Regenerating a binding is byte-stable; bootstrap never overwrites an
existing binding or regenerates an existing CA, and it never deletes,
purges or recreates a stream. NATS `max_payload` is set explicitly to
2097152 (the 2 MiB frame budget of LIVE_CONFIG_SPEC; the server default
of 1 MiB does not fit a full frame with headers).

## Verify it works

```bash
./scripts/verify.sh
```

The script prints the service table, runs the authoritative destination
check for every network with the runtime gateway credentials (account
identity, stream, subject coverage, limits, both D77 metadata keys),
shows the latest `DELIVERY_CONFIRMED` of every adapter and probes the
NATS health endpoint. Expected output ends with `verify: ok`.

Watch the live pipeline:

```bash
./scripts/runbook.sh status         # last control event of every process
./scripts/runbook.sh logs bsc       # follow one circuit
./scripts/runbook.sh tail bsc       # last message of every bsc subject
```

The NATS monitoring UI answers on http://127.0.0.1:18222 (streams,
consumers, message counts).

## Runbook drills

The runbook exercises the E06-09 behaviors as reproducible commands.
Readiness and recovery are observed in the control logs (D52): every
process writes JSON lines with `CONFIG_VALIDATED`, `STORE_OPENED`,
`RECOVERY_STARTED/COMPLETED`, `LIVE_BOUNDARY`, `CAPTURE_STARTED`,
`WAL_SAVED`, `TRANSPORT_RETRY`, `DESTINATION_VERIFIED`,
`CONFIG_BLOCKED`, `DELIVERY_CONFIRMED`, `DRAIN_STARTED/COMPLETED` and
`STOPPED`.

| Drill | What it proves |
|---|---|
| `runbook.sh restart-network bsc` | Restarting one circuit replays its pending WAL and resumes at H+1; the other circuits never restart and keep confirming deliveries. |
| `runbook.sh stop-nats` then `start-nats` | A NATS outage never stops capture: every adapter keeps writing `WAL_SAVED`; after NATS returns, each gateway re-runs the online destination check (`DESTINATION_VERIFIED` with `after: reconnect`) and the backlog drains with identical message ids (dedup, no loss, no duplicates). |
| `runbook.sh drain bsc` | Pending recovery works independently of live capture: with the gateway down the adapter keeps capturing; the drain run then delivers exactly the pending suffix and exits after durable `DRAIN_COMPLETED`. |

## Tear it down

```bash
./scripts/down.sh             # stop everything, keep all volumes
./scripts/down.sh --volumes   # stop and DESTROY all data
```

A plain stop keeps every WAL, journal and the JetStream store; the next
`up.sh` recovers pending delivery from them. `--volumes` is the only
path that deletes data — nothing in the stack removes WALs or streams
automatically.

## Relationship to the demo environment

`e03/demo` is the visualization sandbox: one plain NATS, ad-hoc streams
(`extractor.<net>.transaction`), a mock producer, a SQLite sink and a
dashboard. This stack is its production version: the same three
networks, but with bootstrap-issued bindings and streams, per-network
accounts and credentials, TLS everywhere, D77 metadata, durable WALs and
the control event log. The two coexist on one host (the demo holds
4222/8222/9080/9081, the deployment holds 14222/18222 on loopback).
The demo's sink and dashboard consume demo-shaped subjects directly and
are not wired into this stack; observing the deployment's traffic is the
runbook's `status`, `tail` and the NATS monitoring UI.

## Contracts and boundaries

- The strict YAML files follow LIVE_CONFIG_SPEC v1: unknown and
  duplicate keys are rejected at every level, TLS objects follow the
  tagged-mode rules (mutual for the ingest boundary, server for NATS),
  and there is no environment substitution inside the YAML. The
  `deployconfig` package enforces this for the mocks; `config check` of
  the real CLI (E06-08) keeps the same schema.
- The binding files follow CONTROL_WIRE_CONTRACT exactly: canonical
  generation string, lowercase hex identities, `descriptor_digest` over
  the pinned preimage. The stream metadata keys are the D77 pair,
  computed from the binding, never hand-edited.
- Runtime gateway users hold the least NATS permissions of the
  bootstrap contract: no CREATE/UPDATE/DELETE/PURGE, ever. Bootstrap
  users live only under `secrets/nats/` on the host.
- The CA key (`secrets/ca.key`) stays with the operator and is never
  mounted into a service. Certificates carry deployment/network/role
  identities in the common name; the gateway of a network rejects every
  other identity during the TLS handshake, before any protocol state.
- Per-network ownership is absolute: one WAL volume per adapter, one
  journal volume per gateway, one JetStream store, no shared writable
  path (MOUNT rules of DEPLOYMENT_BOOTSTRAP_CONTRACT).

Testnet profiles (Sepolia, Hoodi, BSC testnet, Amoy) are separate
contours with their own verified manifests per D82 and are not part of
this baseline; mainnet defaults are never inherited by them.

## What is mock and what is real

| Real (contract behavior) | Mock (pre-build stand-in) |
|---|---|
| Strict YAML schemas and validation | Record payloads are small JSON documents |
| Binding descriptors, digests, D77 stream metadata | Ingest wire is length-prefixed JSON over mTLS, not the pinned gRPC protocol |
| NATS accounts, permissions, TLS, max_payload, stream limits | Mock blocks are generated on a fixed cadence (12s ETH, 3s BSC, 2s POLY), not captured from native clients |
| WAL_SAVED after fsync, DELIVERY_CONFIRMED after PubAck, replay of the exact pending suffix | One complete fragment per event (no PART splitting; the frame budget check is still enforced) |
| Nats-Msg-Id in the exact `ex2.` 89-byte tuple form, `Nats-Expected-Stream` header, dedup on retry | |

When the real gateway binary and the native clients with embedded
adapters land, they replace `cmd/mock-gateway` and `cmd/mock-adapter` in
this compose topology; the configuration, bootstrap, accounts, streams
and verification stay unchanged.
