## Findings that changed block 0

The first development run of this probe led to block 0 correction 01 (PR
#175). See [E01-04.early_faults](E01-04.early_faults.md), "Correction 01".

- **Orphan records.** A record beyond the durable counter is not an
  observation. The probe now reads the admission and decision states only
  below the durable counter of the run, as the accepted packages do.
- **Crash on ETH.** On ETH, the crash variant can lose a write that is still
  in Pebble's in-process WAL buffer.
- **Corpus comparison.** The corpus result leaves out only the per-block
  `decisions` rows of `corpus_compare.py`. `exported` names blocks of decided
  IMPORT and CANONICAL decisions only.

## Technical decisions

- **How the fault fires.** The fault store panics inside the store call. It
  does not return an error. The panic unwinds the native caller, so no error
  handler or later write of the step runs, as at a real crash or power loss.
  The block 0 README says "returns an error"; the effect on the step is the
  same, and nothing after the point runs.
- **Opening mode.** The mode after the restart is the gate's opening rule:
  RECOVERY with a boundary, BOOTSTRAP without
  (`extractor/lifecycle` `Open`). The shipped attach finishes recovery and
  goes live inside `AttachLifecycle` when a boundary exists. Its phase is
  kept as `attach_phase`: LIVE in every case with a boundary, and BOOTSTRAP
  in the two cases without one, where the probe's `GoLive` then sets H.
- **Where H is.** The H points use block 1 as the initial sync, so H is
  block 1. The other points set H at the genesis, so block 1 is the first
  live block and the fault block.
- **Freezer.** It stays on the OS file system, in a new directory per open.
  The short chain never reaches it.

## Limits

- Part B is open: the four Geth handoffs.
- The model limits of block 0 apply:
  - only the two extremes of unsynced survival;
  - no torn writes or false syncs;
  - no freezer;
  - the reopen happens in the same process.
- The crash variant reopens on a `CrashClone` at 100 while the abandoned
  node's background goroutines still run on the old file system. The clone
  blocks writes while it copies.
- `unsynced_dropped` is the fault store's count of writes since the last
  completed sync. It is an upper bound.
