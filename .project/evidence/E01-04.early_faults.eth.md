## Run 02 results, private local ETH

Every case passes: 15 points × 2 variants. The judgement found no native
error:

- no restart, `GoLive` or import error;
- no undecided intent;
- the re-import added nothing;
- the native re-execution checks of the accepted corpus driver held in
  every case (one row per block, the root, the gas, one equal receipt per
  transaction).

- **AC-SCP-03-01: PASS**, from both variants of the three H points.
  - `h.before-boundary-sync`: the boundary is lost and the gate opens in
    BOOTSTRAP. The restart sets H at the native head (block 1), and only
    block 2 is exported.
  - `h.after-boundary-sync` and `h.after-golive-before-first-import`: the
    gate opens in RECOVERY and H is kept. The boundary equals the native
    canonical header at block 1, and only block 2 is exported.
- **Opening mode.** It is now read, not derived: the gate's phase from its
  `gate_opened` trace event. It is BOOTSTRAP in the 2 cases without a
  boundary and RECOVERY in the other 28.
- **Recovered obligations.** At the points after the ADMITTED sync, at both
  EXEC_READY points and before the intent sync, the native import of block
  1 was lost with the step. Recovery completes the saved obligation as a
  CANONICAL activation of the stored block, because its parent is no longer
  the head. Each block is delivered exactly once.
- **Pending points.** At every pending point, a power loss dropped at least
  one write (`unsynced_dropped` ≥ 1). The state after the restart is the
  state before the write.

### Finding: on ETH a crash reaches the same states as a power loss

At every pending point the crash case shows the power-loss state. A probe
of the patched tree showed the cause: after a NoSync `Put` and a 300 ms
wait, the WAL file stays at the size of the last synced record, and a
`CrashClone` at 100 does not contain the write. Pebble v2 keeps a small
NoSync WAL record in process memory until a sync or a full WAL block. So on
Geth, a real process crash loses the pending capture write just as a power
loss does.

The probe waits until the WAL files stop growing before the crash copy
(`wal_settle_ms`, about 50 ms). In this run they did not grow. Therefore:

- the recovery paths that only a crash adds (a surviving counter, ADMITTED,
  EXEC_READY, intent, decided, pin or boundary write) are not reached on
  ETH;
- they are reachable on BSC and POLY, whose pebble v1 store-handle close
  flushes the buffer (block 0, "Restart").

This is recorded for qa as a limit of the ETH slot, not as a failure: the
catalog crash sets allow the state before the write.

## Technical decisions

- **How the fault fires.** The fault store panics inside the store call,
  instead of returning an error. The panic unwinds the native caller, so no
  error handler or later write of the step runs, as at a real crash or
  power loss.
- **Opening mode.** The gate phase from `gate_opened`, traced when the gate
  opens inside `AttachLifecycle` and before recovery runs. The shipped
  attach then goes live itself when a boundary exists (`attach_phase`).
- **Where H is.** At the H points, block 1 is the initial sync and H is
  block 1. At the other points H is the genesis, so block 1 is the first
  live block and the fault block.
- **Freezer.** It stays on the OS file system, in a new directory per open.
  The short chain never reaches it.

## Limits

- Part B is open: the four Geth handoffs.
- On ETH the crash variant reaches only the power-loss states at pending
  points (see the finding).
- The model limits of block 0 apply:
  - only the two extremes of unsynced survival;
  - no torn writes or false syncs;
  - no freezer;
  - the reopen is in-process.
- `unsynced_dropped` is the fault store's count of writes since the last
  completed sync, an upper bound.
