## Correction 01 (records 04 at `3ccd95e`)

The first development run of the Geth fault probe (not measured evidence,
not retained; the Geth block's records will reproduce it) raised three
questions for block 0. After review 001 of this correction, the outcome is
as follows.

- **`adm.before-counter-sync` stays as it was.** `Begin` writes and syncs
  the INPUT_PREPARING record, then writes and syncs the counter
  (`adapters/geth/admission/admission.go`, `Begin`). A record beyond the
  durable counter is not an observation: admission `open` loads only
  `[lowwater, counter)`, and the next `Begin` overwrites the orphan. So a
  power loss before the counter sync leaves no observation, as the catalog
  says. The run showed `preparing` because the probe read the raw key. The
  probe is fixed in the Geth block, and the catalog boundary text now names
  the rule. A first version of this correction changed the catalog instead;
  review 001 found that wrong, and it was reverted.
- **Crash variant per family.** A crash keeps the writes that reached the
  file system.
  - ETH: the pebble v2 `CrashClone` at 100 can lose a write that is still in
    Pebble's in-process WAL buffer, because records persist asynchronously.
  - BSC and POLY: closing the pebble v1 store handle flushes and syncs that
    buffer, so every write survives.

  The catalog crash sets already allow both states at every pending point.
- **Corpus result.** After a fault, a recovered obligation can close as a
  CANONICAL activation of the stored block, because its parent is no longer
  the head (`adapters/geth/decision/native/decision.go`, `build`).
  `final.corpus` therefore leaves out only the per-block `decisions` rows of
  `corpus_compare.py`. Its `decisions of other blocks` and `reimport` rows
  still count. `exported` names only blocks of decided IMPORT and CANONICAL
  decisions, never SIDE or FINALITY, so rule 4 still requires exactly one
  delivery per block.

The Python code and the mutant table equal those of records 02 (the test

## Correction 02 (with the BSC block)

The BSC block showed two problems with the pebble v1 restart recipe of
correction 01:

- **The close fails.** Closing the pebble v1 store handle under the
  abandoned chain reports leaked iterators and leaves the chain calling a
  closed store, which panics.
- **The close is not a faithful crash.** A close flushes Pebble's
  in-process WAL buffer, which a real process crash does not do.

Pebble v1's `MemFS` has no crash clone. So the README "Restart" now copies
the chaindata files into a new strict file system without closing:

- as they are, for a crash;
- after `SetIgnoreSyncs(true)` and `ResetToSyncedState`, for a power loss.

A crash now keeps exactly what reached the file system on every family.
Both Pebble versions keep a small NoSync WAL record in process memory, so at
the pending points a crash reaches the same states as a power loss. The
probes showed this on ETH and on BSC. The catalog crash sets allow the state
before the pending write, so the catalog, the judge and their tests are
unchanged. Only the README changes.

## Correction 03

The BSC part B review (PR #179) found that the `*.pass-at-golive` catalog
items say `GoLive` "is refused", while a held import on another goroutine
holds the guard, so `GoLive` waits for it. The README "Catalog" paragraph
on handoffs now states the reading for every family: a concurrent held
import is serialized on the guard; `ErrOrder` applies only to a pass open in
the same guard hold, which the lifecycle unit tests cover. The handoff
passes when `GoLive` does not set H while the import is held (it waits, or
returns `ErrOrder`), H is the held block, and that block is not captured.
The catalog and the judge are unchanged. See
[E01-04.early_faults.bsc](E01-04.early_faults.bsc.md), "Part B".

## Limits

- **Storage model.** The power-loss variant drops unsynced data at the Pebble
  level and tests the two extremes of unsynced survival (all dropped, or all
  kept as the crash variant); mixed survival of native writes is not tested.
  Torn writes, false syncs and file system metadata loss are not
  modeled. The freezer is not in the model; the short private chains never
  reach it.
- **In-process reopen.** Both variants reopen the node in the same process,
  because the store lives in memory. The Bor block also keeps its
  process-crash model.
- **Report truth.** The judge trusts the probe for the states it reports.
  Each client block must read the `after_restart` states from the durable
  records through the accepted packages, read `native_h` from the native
  chain, and take `unsynced_dropped` from its store wrapper. That count
  is an upper bound of the dropped writes.
