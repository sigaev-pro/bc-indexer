# Reader boundary evidence interface

AUT-02 closes the D87 schema obligation already assigned to E01-01.evidence. This is a test artifact interface, not a product wire format or a runtime acceptance shortcut. The normative requirements remain [TESTING_CONTRACT](../docs/TESTING_CONTRACT.md). The harness produces actual boundaries and checks their truth; later reader tasks prove the full comparison and mutation corpus.

The candidate supplies `test/evidence/reader-boundary-manifest.schema.json`, declaring `schema_version: 1`, and supports `kind: "ReaderBoundaryManifest"` in the existing `evidence-artifacts-v1` stdin interface. The context uses the existing registry, allowed owners/tasks/profiles, manifest map, and exact UTF-8 artifact map. No expected validity or vector identifier is passed to the candidate.

## Fields

All fields below are required. Objects reject unknown fields. Text identifiers are nonempty. Digests are lowercase 64-digit SHA-256 values. Artifact references are `{path, sha256}`; every non-null reference must resolve to the exact UTF-8 bytes in `context.artifacts`. Large collections live in these hashed chunk artifacts; this validator does not claim to replay their native or NATS semantics.

- `schema_version`: integer 1.
- `boundary_id`, `artifact_path`: nonempty strings. `artifact_path` is the location of this manifest's own canonical JSON bytes, not a self digest.
- `network`, `profile`, `profile_manifest_digest`, `fork_variant`, `fixture_kind`, `suite`: the six run axes from EVID. Use a concrete runtime profile; DOC and COMMON cannot describe a native reader boundary.
- `case_identities`: a nonempty array of distinct complete eight-field identities. Every identity must match the six axes and an applicable registry entry with its accepted task owner.
- `run_started`: boolean. `run_id` and `run_manifest_path` are nonempty strings after execution starts, otherwise null.
- `run_plan_ref`, `oracle_ref`: artifact references, required after execution starts; otherwise references or null. These bind declared inputs and independent oracle provenance, not proof that an oracle was actually executed.
- `expectation`: `{mode, predicate_ref}`. Mode is `positive_delivery` or `declared_negative`. Positive delivery uses null predicate_ref. A declared negative case requires a hashed reference to its predeclared failure predicate. A reference's presence never proves that predicate occurred.
- `source_boundaries`: an array of objects `{source_id, baseline_ref, admission_set_ref, terminal_frontier_ref, transitions_ref}`. Source IDs are distinct. The four references record baseline, accepted obligations, terminal frontier, and episode/binding/generation transitions. They may be null while incomplete; source closure satisfaction requires at least one source and all four references for every source.
- `delivery_boundaries`: an array of objects `{destination_id, binding_digest, episode_id, generation, manifest_refs, highwater_ref, seal_ref, puback_ref, attempt_census_ref, attempt_classifications_ref}`. Generation is a nonnegative integer; the destination/binding/episode/generation tuple is distinct. manifest_refs is an array of artifact references. The five remaining references may be null while incomplete. Delivery closure satisfaction requires at least one boundary, nonempty manifest_refs, and all five references in each boundary. Attempt classification artifacts preserve ordinary attempts and fence-induced exact retry diagnostics separately.
- `streams`: an array of objects `{stream_id, destination_id, generation, config_ref, lower_sequence, upper_sequence, seal_ref, coverage_ref, raw_message_refs, terminal_fence}`. The stream/destination/generation tuple is distinct. Generation and lower_sequence are nonnegative integers; upper_sequence is null or an integer at least lower_sequence. config_ref, seal_ref, and coverage_ref are nullable references; raw_message_refs is an array of references. The terminal_fence object contains nullable `implementation_ref`, `conformance_ref`, `process_events_ref`, `ingress_restrictions_ref`, and `recovered_frontiers_ref`. Terminal fence satisfaction requires at least one stream and all five fence references for every stream. Stream coverage satisfaction requires at least one stream, all sequence bounds, and configuration/seal/coverage references. A nonempty interval also requires raw_message_refs. The empty interval remains a structural possibility, not proof of no source or delivery obligations.
- `logical_comparison`: `{expected_ref, actual_ref, diff_ref}`, each a nullable artifact reference. Semantic comparison satisfaction requires all three references. An empty diff is still a hashed artifact.
- `phase_times`: exactly six entries, named `startup`, `observation`, `shutdown_drain`, `stream_closure`, `reconstruction`, and `comparison`. Each entry is `{started_at, finished_at, deadline_seconds}`. The timestamps are date-time strings or null; deadline_seconds is finite and positive. A finish requires a start and cannot precede it. Actual timestamps lie within the linked RunManifest's execution interval. Phases may overlap; this schema does not impose an invented sequential runtime schedule. Full positive completion requires both timestamps for every phase, and no phase may exceed its declared deadline in that case.
- `conditions`: exactly `source_closure`, `delivery_closure`, `terminal_fence`, `stream_coverage`, `reconstruction`, and `semantic_comparison`. Each condition is `{status, evidence_refs, reason, missing_obligations}`. Status is `NOT_RUN`, `SATISFIED`, `FAILED`, or `INCOMPLETE`. Reason is nonempty text. evidence_refs and missing_obligations are arrays of artifact references and nonempty text, respectively. SATISFIED requires evidence and no missing obligations. FAILED requires evidence. INCOMPLETE requires at least one missing obligation. NOT_RUN has no evidence and requires an explanation. These statuses do not extend CaseResult verdicts.
- `reader_complete`: boolean, true exactly when the first five conditions above are SATISFIED. A reader may finish while semantic comparison fails.
- `comparison_passed`: true for SATISFIED semantic comparison, false for FAILED, and null for NOT_RUN or INCOMPLETE.

## Binding and consistency

When run_started is true, resolve `context.manifests[run_manifest_path]` and validate it through the existing RunManifest validator, including its artifacts. Its run ID and six axes must match. Its complete case identity set must equal this manifest's case identities. It must contain this artifact_path exactly once in actual_artifacts, with the SHA-256 of this manifest's canonical bytes. Those exact bytes must exist in context.artifacts. Canonical JSON is the existing sorted compact ASCII encoding plus a newline. There is no circular hash: the boundary names the run path/ID without its digest, while the run hashes the boundary artifact.

When run_started is false, all conditions are NOT_RUN; reader_complete is false; comparison_passed is null; run ID/path and all phase timestamps are null; source/delivery/stream arrays are empty; logical comparison references are null. No RunManifest or invented actual execution is required. The profile and registry identities must already be resolved; failure before that point remains an ordinary CaseResult NOT_RUN diagnostic without a fabricated boundary manifest.

A started positive-delivery run whose case outcomes all report PASS requires all six conditions to be SATISFIED and every phase to finish within its deadline. A recorded FAIL may preserve failed, incomplete, or unstarted conditions. A declared negative case may truthfully pass while a positive closure condition fails, but only the later runtime comparator can prove the predeclared predicate and forbidden-output checks. Artifact validation never certifies that proof.

Condition satisfaction requires the referenced structural evidence described above. Hash validity, complete fields, and consistent flags establish artifact conformance only. They do not prove that source frontiers are authoritative, PubAcks are durable, a terminal fence is valid, stream coverage is complete, records reconstruct, or logical values match. Those remain explicit runtime obligations, including every D87 counterexample.
