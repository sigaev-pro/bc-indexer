# Initial evidence task handoff

This is the trusted bootstrap acceptance contract for `E01-01.evidence`, not its implementation. D91 supplies this interface within the accepted D82/EVID requirements. D86 still prohibits actual E01 dispatch. The controller may execute it only after a later reviewed owner launch and accepted BOOT-09.

The future worker owns `test/evidence/`, `.project/evidence/E01-01.evidence.md`, and its status update. It cannot change this contract, the trusted verifier, task recipes, or controller code. It supplies:

- `case-registry.schema.json`, `case-result.schema.json`, and `run-manifest.schema.json`: machine-readable JSON schemas declaring schema version 3 and the D82/EVID fields.
- `profile-registry.json`: `{"schema_version":3,"profiles":{...}}`, mapping the seven accepted profile names to ETH, BSC, or POLY. This definition contains no invented chain configs or runtime hashes.
- `reader-boundary-manifest.schema.json`: the D87 schema version 1 artifact and checks defined in [reader-evidence-contract.md](reader-evidence-contract.md). Runtime boundary production and proof remain later harness/reader obligations.
- `validate.py`: the executable validation interface below, with its real schema and reference checks.
- `README.md`: schema/passport documentation, applicability rules, validation commands, and unresolved runtime inputs.

The accepted requirements are [EVID](../docs/IMPLEMENTATION_GATES.md), [D82](../docs/TESTING_CONTRACT.md), and assigned cases AC-DEV-01-01, AC-DEV-04-02, and AC-DEV-04-03 in [ACCEPTANCE_CASES](../docs/ACCEPTANCE_CASES.md). The existing [corpus](../testing/corpus/README.md) remains authoritative. This interface does not add a product wire format, public profile, fixture-kind enum, runtime verdict, or native execution requirement to this artifact task.

## Candidate validation protocol

The trusted driver invokes `python -I test/evidence/validate.py`. One JSON validation bundle arrives on stdin: `contract: "evidence-artifacts-v1"`, `kind`, `document`, and `context`. Bootstrap examples additionally set `synthetic: true`; that label describes the test input, not its validity. For ordinary validation bundles, exit 0 means valid and exit 2 means invalid; these exit codes are authoritative and empty stdout is allowed. ExpandProfiles requires the checked JSON response described below. Other exit codes, timeout, or a missing required artifact file are failures. Each output stream must remain below 65,536 bytes; reaching the limit fails even when the candidate catches a write error and exits with an expected code. Candidate diagnostics are bounded and hashed. Expected verdicts and vector IDs are kept in the trusted driver and are never passed to the candidate.

`kind` selects `CaseRegistry`, `CaseResult`, `RunManifest`, `CompositeManifest`, `PrerequisitePlan`, or `ReaderBoundaryManifest`. The first three use schema version 3; the D87 reader boundary uses schema version 1. Composite and prerequisite bundles exercise their cross-document and stage constraints. `context` supplies the relevant registry, manifest documents keyed by reference path, artifact text keyed by path, allowed task IDs, profile definitions, and accepted applicability rules. A referenced manifest digest is SHA-256 of sorted compact ASCII JSON plus a newline; artifact digests cover the exact UTF-8 bytes. No circular CaseResult/RunManifest hash is introduced.

Case identities contain all eight D82 fields. Registry records carry task and fixture identities and applicability. CaseResult adds the execution verdict and optional manifest reference according to EVID. RunManifest uses the EVID fields named in the trusted examples, including registry version/digest, exact identities and individual outcomes, source/build information or an explained DOC exclusion, input/expected/actual/log references, independent expected provenance, phase times and deadlines, and parent linkage. The examples are ordinary data; the candidate cannot select behavior by recognizing a vector or a synthetic label.

D91 explicitly selects `network=DOC` for resolved document evidence. D82 already specifies `profile=DOC`, `profile_manifest_digest=NOT_APPLICABLE`, `fork_variant=NOT_APPLICABLE`, and `fixture_kind=document`; it leaves this network spelling unspecified. COMMON remains a definition scope, and DOC is never a production network or runtime profile. Other handoff field spellings are likewise technical test-artifact choices within the accepted EVID semantics, not new product protocol guarantees.

Composite bundles contain a run ID, correlation ID, aggregate verdict, required profiles, child references with individual outcomes, and a separate TC08 integration outcome. Every child reference must match its supplied child manifest. A recorded failed child is valid evidence with an aggregate FAIL; a parent PASS cannot hide it. Missing or duplicate children and mismatched child outcomes are invalid. Prerequisite bundles use the seven existing stage IDs with dependency/evidence lists: native seams are required at E01, delivery proof at E03, and composed proof at E05. A future prerequisite, cycle, unknown dependency, or missing required early evidence is invalid. These evidence labels are stage obligations, not new fixture-kind enums.

Prerequisite examples are synthetic plan-constraint inputs and may contain a partial stage set. The acyclic forward-dependency mutation changes one edge of a valid two-stage control, so detecting cycles alone is insufficient. These examples do not replace the controller's independent reconciliation of the complete 84-task catalog and actual prerequisite gates.

For `kind: "ExpandProfiles"`, stdin instead contains `scope: "ALL" | "ETH" | "BSC" | "POLY"`. The candidate returns the sorted JSON array of concrete accepted profile names on stdout and exit 0. It must not collapse mainnet and testnet or admit an unknown profile.

The trusted pack contains positive and negative schema/reference examples, seven-profile/two-fork/two-suite identity checks, actual profile-expansion calls, and parent/child and prerequisite checks. Negative inputs preserve ordinary fixture identifiers. Future implementation must satisfy the complete source requirements, not merely special-case these examples; independent exact-head review remains mandatory. The pack is deliberately not a product schema validator. Disposable test stubs used to check this bootstrap driver do not establish E01 completion.

## Trusted evidence and handoff

The immutable run recipe pins the verifier, this contract, proof adapter, and recipe file by hash. Changing any pin blocks resume. The controller executes the trusted driver from its accepted source checkout, against the candidate commit, under bounded supervision. It retains required output hashes, the full frozen recipe, verifier source commit, process requests/results, and complete driver logs. Task proof is bound to exact task/head/base and authorization. Native runtime remains NOT_RUN even when artifact conformance passes.

The coordinator publishes `controller_verification` separately from reviewer findings, after verification. Its proof digest covers the complete retained task proof. Receipt import and replay authenticate that field against the actual coordinator comment; a locally edited proof with recomputed hashes fails. Existing exact-head GitHub CI, independent review, capture-before-merge, and verified merge-tree requirements still apply. A plain GitHub capture cannot import a product task without its task proof.

Only this first task is configured. Coordinator plus independent QA review owns additional recipes and adapters; module owners may propose commands and outputs. Later additions require a reviewed fresh run snapshot and an explicit budget/attempt-preserving handoff. The current controller has no general cross-run budget-transfer command: do not create a fresh run to reset consumed limits. Until that handoff is implemented and reviewed, stop with the existing run and retain its state. Resume cannot silently acquire a new verifier, broader authorization, or a fresh budget. This readiness result does not claim unattended completion of the entire E01 stage.
