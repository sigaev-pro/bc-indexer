# Issue-driven development

D95 authorizes this default workflow for the accepted E01 through E07 backlog. The fixed [issue catalog](ISSUE_CATALOG.md), [task dependencies](TASK_DECOMPOSITION.md), specification, and acceptance gates remain authoritative. The project ends at confirmed standardized delivery to NATS. Production deployment requires separate authorization.

## Work one concrete block

1. Select an issue whose dependencies have accepted commits and evidence. Read its specification sections and acceptance criteria. Record the issue, block outcome, allowed paths, base commit, applicable profiles, and required checks in [PROJECT_STATUS](../PROJECT_STATUS.md). Split a large issue into explicit blocks with separate PRs; the parent issue remains open until all its criteria pass. A partial block cannot unlock a dependent task or gate.
2. Use a task branch or isolated worktree with one writer. The coordinator may assign a focused implementer and read-only reviewers. Keep at most three active model sessions, including the coordinator. Record actual session identities in the handoff and review record; no controller launch, session ledger, service installation, or controller adapter is required.
3. Implement the block and run checks that establish its stated result. Save commands, commit/input hashes, profiles, exit codes, failures, and evidence locations. Preserve credentials outside artifacts. Report unavailable checks as NOT_RUN. A build plan, mocked test, or schema check does not prove a native build or live delivery.
4. Commit and push the completed block immediately to its working branch. Open or update a draft PR linked to the issue, with the task ID, exact scope, checks, limitations, and remaining parent criteria. Draft publication does not require a passing stage gate or completed review. Preserve previous failed results; repair with a new commit.
5. Obtain independent Spec and Standards review of the exact commit using the project review workflow. The author applies the [review checklist](REVIEW_CHECKLIST.md) before requesting review, and each reviewer applies it to the exact head. Reviewers inspect the actual diff and relevant evidence, report concrete findings, and return PASS or REQUEST_CHANGES with checks and cleanup. The implementer cannot approve their own change. A changed head requires fresh review of the new head.
6. Merge only after the block's required checks and both review axes pass, the current base is compatible, and branch protection permits the exact head. Keep `bootstrap/ci` and `bootstrap/independent-review`; publish the review status only from actual recorded independent results. Never bypass branch protection, invent a reviewer, or equate bootstrap CI with product acceptance. Serialize merges. Close the parent issue only after all its outputs, profiles, and acceptance criteria have evidence. Record the merge, remaining limitations, and next ready task, then continue without a routine permission request.

For a blocked block, publish the checkpoint with the concrete failure, investigate its cause, and continue only independent ready work. A timeout ends the affected command; it does not end the approved project work. Repeated unchanged failures require a different diagnostic or a smaller block, not another identical attempt.

## Checks and evidence

Use the existing CI, product tests, standalone verifiers, and bounded process helpers directly where they fit the task. Generate evidence figures from a retained run with `test/harness/evidence_summary.py` instead of copying them by hand, and prove new checks with single-check mutants from `test/mutate.py`. A missing controller recipe or pending legacy run is not a development blocker. Add task-specific tests as part of the product issue instead of extending orchestration. Keep independent expected results separate from the implementation they judge.

Every runtime claim identifies the actual source commit, pinned inputs, network/profile, suite, run ID, commands, outputs, and cleanup. Give each direct run a new evidence directory. Keep the old failed canonical run and its evidence unchanged; a new direct run does not repair or replace it. Record failures and repaired reruns separately under D83. Only preparation-complete runtime execution counts toward the 1,800-second standard-run limit; preparation and compilation are separate phases. Volumes and profiles remain configurable. Ethereum evidence does not stand in for BSC, Polygon, or testnets.

The existing acceptance collectors and proof formats remain useful for verifying evidence. They are optional workflow tools, not the sole way to dispatch work or authorize a merge. Actual issue criteria, independent review, profile coverage, and branch protection remain mandatory. A partial PR's evidence establishes only its declared block, never the entire parent task.

## Legacy controller work

The controller, launch ledgers, recipes, services, old receipts, and [AUT06 draft PR #106](https://github.com/sigaev-pro/bc-indexer/pull/106) remain retained. They are inactive by default. Do not install/start services, resume the old run, clear its pending failure, reserve controller sessions, or complete AUT06 merely to start product work. Use the [legacy automation guide](../automation/README.md) only for an explicitly scoped legacy diagnostic or reuse of an existing standalone check. Re-entering controller maintenance requires a concrete product need and an explicit task scope; it must not silently replace the current product block.
