Это повторная документальная проверка с контрпримерами, а не запуск системы и не рецензия другого человека. Исходники клиентов и актуальность внешних релизов заново целиком не переаттестовывались. Доказательства ниже описывают исходную базу 1e97c11 и не являются утверждением, что исправленный IR-02 всё ещё присутствует. Предыдущие F01–F14 остаются историей закрытого пакета D73–D79; новый проход не подменяет их статус новым общим «всё идеально».

## IR-01 — CallFrame: адрес попытки и адрес успешного создания

**Доказательство.** В подробном ТЗ на базе `1e97c11`, строки 338–356, ранний перечень CallFrame требует `created_address` как адрес создаваемого контракта «когда определён», а также `runtime` и `native_type`. Его копия находится в каноническом v3, строки 181–199. При этом [MESSAGE_CONTRACT, §3](MESSAGE_CONTRACT.md#3-transactionrecord), строка 61, задаёт закрытый CallFrame с отдельными `attempted_create_address` и `created_address`, `engine` и `kind`, без полей runtime/native_type. [CURRENT_SEMANTICS, Block/calls](CURRENT_SEMANTICS.md#block-calls-и-account-changes), строка 15, разрешает `created_address` только при локальном успехе; отмена успешного создания предком отдельно отражается effects_committed и AccountChange.

**Контрпример.** CREATE2 определил адрес A, затем constructor завершился REVERT. По старому перечню адрес уже определён, значит A можно положить в created_address. По точному контракту A должен находиться только в attempted_create_address, а created_address отсутствует. Один и тот же fixture допускает два несовместимых прочтения. Формальная приоритетность подробной модели помогает интерпретировать документ, но не устраняет противоречащий ей обязательный перечень.

**Исправление.** В раннем перечне использовать точные имена принятой модели; для создания прямо указать обе ссылки и условия присутствия. Runtime/type описать как уже существующие engine/kind и profile provenance, не добавляя новые wire fields. Не менять локальный успех на конечное существование: successful CREATE внутри reverted ancestor по-прежнему может иметь created_address при effects_committed=false. В неизменяемом v2 исправления не делать.

**Проверка.** Варианты: адрес определён + constructor revert; локальный success + ancestor revert; локальный success + сохранённый результат; frame, где native ещё не определил адрес. Для каждого оба описания дают одинаковое presence. Использовать REQ-DAT-04 / AC-DAT-04-01, E04-01.calls; структурное presence проверяет E02-02.schemas. Не создавать второй источник истины для CallFrame.

**Что требует решения.** Новая продуктовая семантика не нужна: достаточно подтвердить применение уже принятого точного контракта ко всем его пересказам. Это не изменение гарантии или расширение объёма данных.

## IR-02 — sources_binding_digest отсутствует в перечнях полей Polygon evidence

**Закрыто D80:** поле Hash32 добавлено в SourceObservationRef и L1Checkpoint. Добавлены AC-LIF-07-07 (schema), AC-LIF-07-08 (смена файла), AC-LIF-07-09 (replay). Narrower whitelist без source_evidence сохранён как допустимый случай. Runtime NOT_RUN.

**Доказательство.** [CURRENT_SEMANTICS, provisioning](CURRENT_SEMANTICS.md#provisioning-supporting-identities), строка 132, требует `sources_binding_digest=SHA256(file_bytes)` в обеих source evidence и сохранение прежней provenance после замены файла. Но в этом же документе SourceObservationRef (строка 103) и L1Checkpoint (строка 111) перечислены без такого поля. В подробном ТЗ это строки 872, 880 и 901 соответственно. По закрытой схеме нельзя просто положить его в произвольный JSON/Any.

**Контрпример.** Observation O1 получен с файлом источников S1. После штатной замены конфигурации новый observation O2 использует S2; различие может состоять даже только в whitespace, которое по принятой формуле меняет digest. В обоих случаях сеть, endpoint и deployment IDs могут совпадать. Одна реализация сохранит digest только в локальном журнале, другая добавит поле в публичный тип, третья не передаст его вообще, следуя исчерпывающему перечню полей. Однозначного результата wire-проверки нет.

**Исправление.** Явно добавить обязательный `sources_binding_digest:Hash32` в SourceObservationRef и L1Checkpoint. Значение брать из проверенных bytes файла, закреплённых для соответствующего observation, а не вычислять из актуального файла во время поздней сериализации/replay. O1 сохраняет digest S1, O2 — digest S2. Это SHA-256 bytes, не новый ID источника и не удалённая аттестация. Не требовать выдуманный SourceObservationRef/digest у допустимого narrower whitelist без source_evidence. Generated field tags остаются задачей E02; семантика и присутствие должны быть определены в ТЗ сейчас.

**Проверка.** В REQ-LIF-07 / E05-01.polygon_observer добавить отдельный AC для S1 → restart/config replacement → S2, включая whitespace-only change: O1 не переписан, O2 содержит новый digest, replay O1 побайтно прежний. Для E02-10.closed_profiles / E02-02.schemas проверить Hash32 width и обязательное presence в двух типах. Сохранить AC-LIF-07-01: восстановленный whitelist без полного source evidence не получает выдуманных данных. Обновить task mapping и полную карточку observer вместе со сценарием.

**Что требует решения.** Подтвердить точное размещение уже требуемого digest в этих двух typed records. Альтернатива «только локально» меняет смысл фразы о передаваемом evidence и должна быть явно описана, а не выбрана исполнителем самостоятельно. Рекомендован вариант с двумя полями.

## IR-03 — остаточные заявления о незавершённом проектировании

**Доказательство.** [LIVE_CONFIG_SPEC](LIVE_CONFIG_SPEC.md), строка 13: «конкретные значения ещё уточняются», хотя NODE_DEPLOYMENT_SPEC/DEPLOYMENT_BOOTSTRAP_CONTRACT уже задают defaults. [MESSAGE_CONTRACT, формат фрагментов](MESSAGE_CONTRACT.md#61-типизированный-формат-recordfragment--d73), строка 170: «отдельные открытые вопросы о содержании native схем» без ссылки на реестр таких вопросов. В подробном ТЗ это строки 1347 и 654. Это остатки прежней стадии, соседствующие с финальным статусом D79.

**Контрпример.** Исполнитель должен решить, начинать ли E02 по принятой модели или ждать ещё не названных решений владельца. Принимающий решения видит закрытый аудит, а исполнитель — указание на неизвестные открытые требования. Это редакционная неопределённость статуса, не обнаруженный сбой системы.

**Исправление.** Указать, что defaults и текущая логическая модель определены; числовой registry tags/type_key, generated schemas, artifact locks и runtime proof являются предусмотренными результатами задач. Новые противоречия проходят обычную фиксацию и согласование. Не объявлять исходные вопросы открытыми без конкретного ID. Отдельно сохранить реальные ограничения этой рецензии и OPEN_PROPOSAL IR-01/IR-02, пока они не разрешены.

**Проверка.** Поиск по обоим ТЗ и нормативным источникам не оставляет безымянных pending design decisions; TODO реализации не превращается в закрытый runtime gate. Это редактура без новых REQ и runtime AC.

## Сквозные сценарии, разобранные при рецензии

«Согласовано» в таблице означает, что в документах найдено непротиворечивое правило для указанного сценария. Это не результат исполнения.

| Сценарий | Документальный результат |
|---|---|
| Offline startup при недоступном Gateway/NATS | Локальный binding задан до capture; сеть не нужна для безопасного принятия новых обязательств |
| Crash до/после ADMITTED, включая динамический ответ Heimdall | Отделены неподтверждённая подготовка и принятое обязательство; ответ сохраняется до передачи native execution |
| EXEC_READY до commit native state | Native-only replay из pin/capsule не заменяет immutable corpus и не создаёт повторные public IDs |
| Multi-block reorg / finality-only decision / отсутствие public events | Один полный batch / один полный batch / checkpoint без batch; chunks не меняют границу |
| Повтор незавершённого Prepare, включая потерю ответа | BeginPrepare возвращает offset или прежнюю reservation; отсутствие PREPARING в GetBatchState не создаёт тупик, поскольку это не единственный recovery RPC |
| Gateway loss до SEALED и после SEALED | До SEALED разрешён новый неопубликованный plan; после SEALED IMPORT_SEALED сохраняет старые bytes/epoch/sequence |
| Partial PubAck, потеря IngestAck, cleanup и Gateway loss | Полный batch ACK обязателен; полный IngestAck/outbox остаётся для RecoveryRelease |
| Release с потерянным ответом и поздний callback | Ordered prefix и publisher/session barriers запрещают resurrection; callback не создаёт отсутствующие записи |
| Drain/cutover/Resume с потерянным ответом | Durable intent/MAINTENANCE, old/new identity и отдельная admission generation описаны; новый desired файл не завершает переход сам |
| Большая запись, большое поле, малый NATS frame | Разделены typed RecordFragment и transport FragmentPart; bounded buffers не означают усечение записи |
| Constructor revert / успешный child с ancestor revert | Точная модель различает попытку, локальный успех и конечный state; ранний пересказ требует IR-01 |
| Polygon unavailable source, новый finalized F2, config replacement | Finality/GC не блокируют готовую delivery; точное поле config provenance требует IR-02 |
| Нет полного набора результатов вариантов | CaseRegistry/CaseResult блокируют gate при пропуске, FAIL, NOT_RUN или неверном evidence; исключения требуют rule |

Не признаны дефектами: отсутствие production consumer, history/backfill, performance SLO, HA/backup и post-ACK архива — согласованные исключения. Optional расширения OFF не блокируют обязательный профиль. Само поле activation_id внутри multi-block decision не обязано быть глобально уникальным: полная ActivationRef квалифицирована inclusion/block и producer/run. Независимая рецензия не вводит новые требования через эти исключения.

## Механическая сверка и следующий шаг

На базе рецензии: 63 REQ, 195 AC, 68 child tasks, 7 gates; все AC назначены, неизвестных parents/dependencies и циклов нет. 15 нормативных зеркал согласованы. Проверка ссылок, anchors, diff и SHA-256 неизменяемого v2 повторяется после сохранения отчёта; итог записывается в PROJECT_STATUS. Оба адресных ТЗ и их канонический контракт при рецензии не меняются.

После D80 следующий шаг — рассмотреть IR-01 и IR-03; IR-02 повторного согласования не требует. После принятия — синхронная правка источников, v3, двух ТЗ по затронутому содержанию, AC/task mapping и повторная документальная сверка. Реализация не предлагается и не выполняется.
