## Существенные несогласования и пробелы

### F01. Относительные пути одновременно разрешены и отвергаются

- **Места:** `TZ_EXECUTOR.md:1220`, `:1242`, `:1808`, `:1971`.
- **Факт:** YAML-контракт разрешает относительные пути и разрешает их относительно файла конфигурации. AC-OPS-01-01 включает `relative path` в обязательные отрицательные варианты и требует field error. Все перечисленные варианты AC должны проверяться независимо.
- **Контрпример:** `storage.live_dir: ./wal` обязан быть принят по контракту и отклонён по AC. Ограничение absolute-only для Polygon `sources_file` задано отдельно; AC не ограничен этим полем.
- **Направление исправления:** положительный сценарий для разрешённых relative paths; отрицательный — для конкретного absolute-only поля. Принятое поведение уже известно, нового продуктового решения не нужно.

### F02. Единица delivery batch описана двумя способами

- **Места:** `TZ_EXECUTOR.md:558`, `:603` против `:856`, `:862`, `:938`, `:1068`.
- **Факт:** контракт сообщений говорит о сообщениях блока и `block batch`; протокол атомарно связывает batch с native canonical/lifecycle decision. Такой decision может содержать много блоков при reorg либо только обновление финальности.
- **Контрпример:** при замене двух блоков двумя другими один исполнитель создаёт четыре block batches, другой — один decision batch. Граница atomic decision→batch и подтверждения получается разной.
- **Направление исправления:** явно закрепить cardinality decision/batch, включая отсутствие public events, много-блочный reorg и finality-only decision; привести раннее описание к принятому автомату. Это согласование уже описанного протокола, а не предложение нового типа публичных сообщений.

### F03. Порядок действий и rollback scope описаны недостаточно точно

- **Места:** `TZ_EXECUTOR.md:537`, `:541`, `:601`, `:694`, `:700`, `:878`, `:1066`.
- **Факт:** `execution_order` присутствует у CallFrame, ExecutionAction и BalanceAction; на него опирается восстановление execution chronology. Не определены общий или отдельные счётчики для этих списков, допустимость совпадений и связь порядка SELFDESTRUCT с его денежной проекцией. У optional `rollback_scope` не определены публичный тип и объект ссылки. Внутренние native snapshot IDs этого не заменяют.
- **Контрпример:** один normalizer нумерует GAS_PURCHASE, root frame, SELFDESTRUCT и BalanceAction единым счётчиком; другой нумерует каждый список отдельно. Оба сохраняют порядок внутри списков, но получатель восстанавливает разную общую последовательность.
- **Направление исправления:** уточнить единую модель порядка либо явные отдельные порядки и правила сопоставления; определить rollback_scope и его область. ID frame/action и их tx-scoped u64 уже заданы на строке 1066 — их отсутствие не является замечанием. Здесь нужно завершить технический контракт; если варианты меняют обещанную наблюдаемую хронологию, выбор следует зафиксировать как решение.

### F04. Модель результатов приёмки не полностью связана с evidence

- **Места:** `TZ_EXECUTOR.md:1808`, `:2086–2093`, `:2313`.
- **Факт:** самостоятельный результат требуется для `(AC ID, network, variant)`; указаны NOT_APPLICABLE и NOT_ENABLED. Обязательная схема manifest перечисляет requirement IDs, task и fixture, но не AC ID или variant ID; её статусы — PASS/FAIL/NOT_RUN/DEFERRED. Задача E01-01.evidence при этом обещает связь с AC.
- **Контрпример:** два обязательных варианта одной AC имеют один fixture/version. Manifest с REQ и PASS не устанавливает однозначно, какой вариант проверен. Исключённый вариант не имеет определённого представления в принятой схеме результата.
- **Направление исправления:** задать case/result identity и связь applicability с run verdict. Допустимы отдельные applicability matrix и run manifests, но их связь и правила итогового gate должны быть явными. Объединять все статусы в один enum необязательно.

### F05. Нормативный текст содержит два набора child task IDs

- **Места:** `TZ_EXECUTOR.md:2054–2056`, `:2155`, `:2284–2289`, `:2313–2324`.
- **Факт:** раннее обязательное разбиение E01-01 использует `.build.ETH/BSC/POLY`, `.supporting`, `.harness`, `.artifacts`; E01-02 — `.ownership`, `.pin`, `.decision` и другие. Итоговый каталог использует `.builds`, `.evidence`, `.pins`, `.owned_capture`, `.decision_bridge` и сетевые applicability slots. IDs объявлены постоянными, зависимости — только перечисленными; явного соответствия двух наборов нет.
- **Последствие:** перенос в трекер создаст лишние либо потерянные задачи и несовпадающие ссылки evidence. Формально корректный граф последней таблицы не устраняет конфликт с предыдущим предписанием.
- **Направление исправления:** один нормативный каталог child IDs; прежнее разбиение заменить ссылкой на него или явно ненормативной исторической пометкой. Нового продуктового решения не нужно.

### F06. В картах соединений пропущен обязательный доступ Bor к L1

- **Места:** `TZ_EXECUTOR.md:763–769`, `:1241` против `:1381–1388`, `:1611–1619`.
- **Факт:** PolygonCheckpointObserver внутри Bor обязан читать supporting Polygon L1 Geth. Карты соединений и клиентов порта 8545 перечисляют только Heimdall как клиента L1 Geth; `polygon-bor → polygon-l1-geth:8545` отсутствует.
- **Последствие:** человек, строящий правила доступа только по таблицам окружения, может исключить нужную связь; проверка checkpoint и очистка recovery-state тогда не продвинутся. Это риск неполной схемы, не утверждение, что существующая Compose bridge блокирует соединение: deploy-файлы ещё не создавались.
- **Направление исправления:** добавить принятую D63 связь в обе таблицы и в проверку доступов. Сам протокол уже задан; нового решения не нужно.

### F07. Краткое ТЗ не показывает весь обязательный объём state diff

- **Места:** `TZ_DECISION_MAKER.md:19–33`, `:48`; `TZ_EXECUTOR.md:543`, `:696`.
- **Факт:** краткий список обязательных данных объясняет баланс и вызовы, но не итоговые изменения nonce, code, storage и существования account. Подробный контракт требует эти данные, включая before/after code bytes при изменении.
- **Последствие:** принимающий решение получает неполное представление о результате и объёме данных. Исходные события упомянуты в кратком файле на строке 48; их полное отсутствие не утверждается.
- **Направление исправления:** добавить понятное описание обязательных изменений состояния аккаунтов и storage в краткое ТЗ. Это раскрытие уже принятого требования.

## Неоднозначная и устаревшая редактура

### F08. Неудачно обозначена длительность хранения IngestAck

- **Места:** `TZ_EXECUTOR.md:967`, `:1152` против `:960–963`, `:987`, `:1934`.
- **Факт:** формулировки «до producer cleanup» и «до cleanup» допускают прочтение как конец срока хранения полного ACK. Переходы и AC требуют сохранить ACK/outbox после удаления payload до подтверждённого Release.
- **Риск прочтения:** удаление ACK вместе с payload делает RecoveryRelease невозможным после потери Gateway store. Другие разделы уже запрещают это; новый дефект самого принятого протокола не доказан.
- **Направление исправления:** раздельно назвать payload cleanup и retirement ACK/outbox после ReleaseAck. Уточнение следует из существующих правил.

### F09. Слишком широко сформулирована неизменность bytes

- **Места:** `TZ_EXECUTOR.md:965`, `:975`, `:1068`, `:1922`.
- **Факт:** «Любые bytes под существующим immutable event_id неизменны» не различает Envelope и transport frame. При потере Gateway до SEALED допускается новая reservation/plan при прежнем READY; publication epoch/layout транспортного представления могут измениться.
- **Риск прочтения:** запретить разрешённое восстановление READY либо ошибочно разрешить изменение уже SEALED frames. Остальные правила различают эти стадии, поэтому это замечание к формулировке, а не доказанный механизм потери данных.
- **Направление исправления:** явно разделить immutable Envelope после READY и immutable frame/header/plan после SEALED.

### F10. В текущем контракте остались фрагменты предыдущих редакций

- **Места:** `TZ_EXECUTOR.md:556`, `:577`, `:599`, `:618`, `:1193–1195`, `:1328–1330`, `:1412`, `:1511–1533`, `:1665`.
- **Факт:** Classic/AVM и live/history описываются местами в настоящем времени, хотя текущий scope исключает их и рядом встречаются deferred-пометки. Старые вступления говорят, что параметры ещё не утверждены, хотя поздние разделы уже фиксируют defaults/flags/mount mappings. Сохранён также отдельный список Rust/tonic источников без актуальной роли в выбранном стеке.
- **Последствие:** читатель не отличает закрытое решение, отложенную функцию и ещё не выполненную runtime-проверку. Текущие границы в других разделах заданы, поэтому эти фрагменты не считаются новыми обязательствами автоматически.
- **Направление исправления:** убрать из текущего контракта исторические предписания либо явно вынести их в ненормативный контекст; оставить неопределённость только там, где она действительно существует. Принятые D38/D42/D64 не переоткрывать.

## Что проверка подтвердила

- Три сети и изоляция owners, live-boundary и отдельное recovery обязательств, отсутствие обещания автоматической истории.
- Различие попытки/rollback/committed effects, SELFDESTRUCT и итогового существования account; комиссии без двойного суммирования; source receipts и tx boundaries BSC/Bor.
- Отличие transport ACK от downstream обработки и от recovery-state GC; раздельные источники BSC finality; критерий Polygon GC через finalized supporting L1.
- Durable native decision, READY/SEALED, fencing, lost replies/store loss, ordered Release, drain/cutover и ограничения несовместимого обновления на уровне описанного протокола.
- Явное разделение документального SPECIFIED и runtime NOT_RUN. Отсутствие implementation proofs не выдано за дефект описанной системы или за её работоспособность.

Структурные проверки: 63 REQ, 156 AC и 68 child tasks сохраняются; normative body адресного файла совпадает с v3 после нормализации ссылок. Видимые ТЗ побайтно равны проверенному commit. Локальные ссылки/anchors и git diff --check проверяются при фиксации отчёта. Исходный v2 не изменён.
