# Полный тестовый контур и профили сетей

D82–D87, 2026-11-06. D84 authorizes implementation through the issue/gate process. Product runtime remains NOT_RUN. The D70 product boundary is NATS JetStream; reader/driver/oracle are test tools. D87 specifies TEST-OPEN-01 subject to independent BOOT-07 acceptance; BOOT-08 owns the remaining TEST-OPEN-02 corpus decision.

## Реестр профилей

Поддержка проектируется для семи публичных профилей трёх семейств. Это обязательный объём приёмки, а не утверждение о проверенной совместимости сборок. `network` остаётся семейством ETH/BSC/POLY; `profile` различает конкретную сеть. CLI/YAML принимает только закрытый реестр LIVE_CONFIG_SPEC; произвольный chain ID или EVM-совместимость не добавляет адаптер.

- ETH: `ethereum-mainnet`, `ethereum-sepolia`, `ethereum-hoodi`; Geth + consensus client.
- BSC: `bsc-mainnet`, `bsc-testnet`; BSC native client.
- POLY: `polygon-pos-mainnet`, `polygon-pos-amoy`; Bor + Heimdall + собственная L1 execution/consensus пара каждого профиля. L1 mainnet для Polygon mainnet; L1 Sepolia для Amoy. Нет fallback на основной ETH extractor или на L1 другого профиля.

Основания реестра: [Ethereum networks](https://ethereum.org/developers/docs/networks/) указывает Sepolia и Hoodi; [BSC network endpoints](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/json-rpc-endpoint/) — BSC mainnet/testnet; [Polygon Amoy](https://polygon.technology/blog/introducing-the-amoy-testnet-for-polygon-pos) — Amoy и L1 Sepolia. Источники просмотрены 2026-11-06; они подтверждают назначение сетей, не runtime совместимость закреплённых клиентов. Устаревшие/закрытые и временные devnet не получают статус публичного supported profile автоматически. Перед выпуском реестр сверяется с официальными источниками; появление/закрытие сети требует явной ревизии профилей и приёмки, не молчаливого исключения из gate.

Для каждого профиля E01/E06 формируют versioned ProfileManifest: profile/family; chain ID и genesis hash; полные native chain/fork config с digest; execution/consensus/supporting commits и image digests; toolchain/patch/dependency lock; bootstrap artifact sources и hashes; поддерживаемые fork ranges и native transaction/system types; параметры finality/GC и Polygon RootChain/Heimdall/L1 identity; state backend/pruning; ENV_READY identity. Значения берутся из проверенных native конфигов и официальных artifacts, не копируются из mainnet по сходству названий. Незаполненный или несовместимый manifest блокирует runtime admission и приёмку; имя testnet само по себе не достаточный proof. D83 задаёт управляемый version-updater workflow ниже: compatible pins обновляются через candidate/gate; изменение scope/семантики требует отдельного решения.

Таблицы типов и семантики задают семейство; конкретный активный набор определяется profile/fork manifest. Неизвестный обязательный native тип или путь блокирует gate, не отбрасывается. Все семь профилей имеют отдельные network identity, bindings, subjects/streams, credentials и writable stores. Имя профиля не заменяет проверку genesis/chain config. Смена mainnet на testnet не является переносом накопленного state: создаётся независимый контур.

## Один стенд, разные виды прогонов

Единая test-only точка запуска принимает выбранные profiles (один, несколько или весь реестр), suite, fixture version, seed, resource/deadline manifest и output directory. Точное написание команды входит в паспорт runner E01; это не новая production команда адаптера. Поднимаются необходимые native/supporting компоненты, адаптеры, отдельные Gateway, настоящий NATS JetStream, независимый reader и сценарный driver. Production reader/consumer в поставку продукта не добавляется.

Каждый запуск использует собственные stores, bindings, namespaces и secrets; immutable input artifacts допускается разделять read-only. До старта проверяются hashes и совместимость fixture/state/клиентов, свободные ресурсы и единственный writer. Готовность определяется native boundary и delivery admission, не только живым процессом. Ошибка подготовки не даёт PASS. Logs и artifacts сохраняются при сбое; очистка затрагивает только ресурсы данного run. Повторный запуск не зависит от предыдущего.

Режимы закрыты: `quick`, `functional`, `fault`, `soak`, `public-smoke`. Каждый applicable case получает явные suite assignments; отсутствие назначения — ошибка реестра. Полная приёмка объединяет обязательные результаты всех режимов, не подменяется quick.

- `quick`: минимальный сквозной corpus каждого выбранного профиля — пустой блок, перевод, контракт/log/storage, полный и вложенный revert, CREATE/CREATE2, пересечение fragment/frame границы; для нескольких профилей также изоляция потоков. Использует подготовленные малые fixtures, без download/full sync и без ожидания случайного публичного события.
- `functional`: все применимые semantic/config/lifecycle/delivery сценарии и границы поддерживаемых fork/types. Expected фиксируется до запуска независимо от проверяемого normalizer.
- `fault`: заданные сбои до/после durable boundaries и составные сценарии; обычный process crash отдельно от потери volatile state/OS cache. Каждый поддерживаемый storage failure model указан явно.
- `soak`: длительные очереди/повторные подключения/ресурсное давление плюс seeded генерация валидных и ошибочных сценариев. Seed, число операций, продолжительность и минимальные quotas фиксируются до запуска; досрочное завершение не PASS. Найденный counterexample минимизируется и добавляется в deterministic corpus.
- `public-smoke`: настоящий поток каждого mainnet/testnet на подготовленной синхронизированной ноде, отдельный manifest. Для testnet дополнительно контролируемые транзакции с сохранёнными inputs/tx hashes и ожидаемыми эффектами; signer ограничен testnet chain identity, mainnet ключи/средства не используются. Mainnet smoke пассивен. Нет faucet/связи/нужных блоков — NOT_RUN до начала либо FAIL по deadline начатого run, не N/A и не PASS.

Подготовка images/fixtures и публичной синхронизации — отдельная фаза. Для локальных прогонов нужны небольшие versioned native state/blocks/fork fixtures и управляемый импорт новых блоков. Mock VM/RPC trace не заменяет native execution; native import equivalence проверяется отдельно для каждого профиля. Seam fixtures можно использовать на ранних gates, но они не закрывают full-process E2E. Consensus/supporting ответы могут быть фиксированными в явно обозначенном seam test; полный E2E использует необходимые реальные компоненты и native interfaces, а публичный smoke никогда не выдаётся за mocked run.

Fixture manifest различает `native-seam`, `local-e2e`, `public`; содержит source profile/fork, фактические genesis/chain config, native state format, pins/retained inputs, blocks/transactions, supporting inputs, воспроизводимый способ подготовки и независимый expected. Локально изменённый genesis помечается как test-only identity: соответствие публичному профилю — отдельное доказательство, не равенство network digest. Запрещены скрытый готовый datadir автора и необъяснимый бинарный snapshot. Полный архив mainnet не prerequisite локального теста. Ни один тип fixture не заменяет недостающий другой.

Resource/deadline manifest закрепляет CPU/architecture/RAM/disk/parallelism, конечные startup/event/total deadlines и soak budget. По D83 сам стандартный прогон выбранного набора профилей занимает не более 1800 секунд wall-clock: от начала сценарного исполнения после PREPARED/READY до формирования результата reader/comparator. При параллельном запуске это предел parent run, не отдельные 30 минут на каждый профиль. Создание/загрузка images и fixtures, bootstrap/sync, развёртывание тестовых контрактов и подготовка funding относятся к подготовке; teardown — отдельная фаза. Все фазы имеют отдельные timestamps, конечные deadlines и diagnostics; подготовка не должна тайно исполнять проверяемые действия или выдавать их за результаты run. Restart/recovery/fault delays, если это действия сценария, входят в measured run. Подготовка не входит в 30 минут, но не может завершиться ложным PASS. Первая попытка и единственный диагностический retry — отдельные runs, каждый с собственным бюджетом.

Режим standard допускает только total deadline ≤1800 секунд. Длительные/нагрузочные soak-прогоны явно выбираются отдельно как extended с настраиваемыми duration/volumes/deadlines; они не объявляются 30-минутным standard PASS. Полная матрица может включать несколько самостоятельных прогонов и не обязана целиком укладываться в 30 минут; её нельзя сокращать для получения зелёного gate. На неподходящих ресурсах preparation сообщает невозможность выполнить заявленный plan вместо молчаливого снижения покрытия. В quick запрещены публичная синхронизация и скачивание входных artifacts; missing inputs обнаруживаются на preparation. Это требования к времени тестов, не production TPS/SLO D40; фактическая достижимость ещё не измерена.

## Обязательные семейства сценариев

Все варианты из ACCEPTANCE_CASES сохраняются; каталог ниже расширяет corpus, не разрешает заменить его одним примером на семейство. В CaseRegistry каждому перечисленному варианту присваивается стабильный variant_id и ожидаемый результат.

- TC01 — startup/identity: один профиль, все профили, неверные genesis/fork/backend/pruning/build, повторный чистый запуск, несовместимый fixture, независимость mainnet/testnet одного семейства.
- TC02 — execution: все поддержанные native transaction types, пустые/плотные блоки, transfer, ERC-20/721/1155 как источники native calls/logs (без нового бизнес-декодера), nested call/delegatecall/staticcall, recursion, precompiles, CREATE/CREATE2 и попытки создания, code/nonce/storage/balances, SELFDESTRUCT и делегирование по применимым fork rules; system/native actions каждой сети. Успех/revert/out-of-gas/native ошибки, вложенный перехваченный откат, fees/refunds и точные consensus receipt bytes.
- TC03 — chain lifecycle: альтернативные ветви, reorg внутри сохранённого recovery range и за его пределами (ожидается уже заданный safety verdict, не новая гарантия восстановления), возврат блока, known branch, no-event decision, status/finality/GC evidence. Рестарт до/после каждого перехода, отдельные BSC vote/header источники и Polygon milestone/checkpoint/L1 критерии.
- TC04 — encoding/size: пустое/отсутствующее/нулевое значение; минимумы/максимумы каждого типа и ошибки ширины/enum; размеры B−1/B/B+1 вокруг каждой fragment/blob/frame/header границы; много частей, большой record, multiblock batch; exact bytes/digests; обрыв/конфликт/неполнота parts. Invalid wire подаётся test injector/validator, не объявляется валидным native output.
- TC05 — delivery: отключение/перезапуск NATS/Gateway, publish принят без наблюдаемого PubAck, потеря reply, exact duplicate и conflicting duplicate, reconnect, partial batch, поздние подтверждения, доступные consumer redeliveries; различать допустимый порядок сообщений и нарушение принятого lifecycle. Runtime consumer ACK не заменяет producer PubAck и delivery protocol.
- TC06 — durability/resources: crash в каждой предписанной protocol sync/marker boundary, отдельно power loss model, потеря одного owner store, corrupted/truncated WAL, slow/full disk, RAM bound и безопасная VM pause, долгий NATS outage, накопление/осушение backlog. Нормальный backpressure и fatal failure сверяются с принятыми правилами, не изобретается drop policy.
- TC07 — operation/security: bootstrap/restart/drain/cutover, compatible replay и incompatible upgrade refusal, credentials/TLS/CA rotation и отказ доступа, неправильные stream metadata/limits/account/subjects, неподдержанный YAML/profile, read-only config check, single-writer/store isolation, допустимые пути. Негативный сценарий получает PASS только при наблюдаемом ожидаемом отказе и отсутствии запрещённых побочных эффектов.
- TC08 — concurrency: разные семейства и mainnet/testnet одного семейства одновременно, все семь профилей, остановка/задержка одного при продолжающихся остальных, независимые streams/credentials/stores. Общий NATS outage отдельно: он может остановить доставку всех, и не считается нарушением изоляции сети.
- TC09 — verifier/mutations: удаление фрагмента/события, изменение bytes/digest/order/scope/network/profile, недостающий expected record, неожиданная запись, конфликт ID, неправомерный PASS/исключение/устаревший manifest. Comparator обязан отвергать каждую предписанную mutation; exact duplicate допускается. Положительный corpus обязателен, постоянно отвечающий FAIL verifier тоже не проходит.
- TC10 — fork/version: каждый поддержанный fork interval и переход в управляемых fixtures, без добавления historical export в продукт; старые/новые native типы, marker/storage/schema совместимость, immutable replay pending. Невозможно получить старый PASS для нового commit/config/profile/fixture без требуемого rerun.
- TC11 — soak/seed: устойчивый steady state и backlog recovery при заданных ограничениях, длительные повторы, seeded последовательности действий и faults. Проверяются invariants completeness/bounded memory/immutable bytes/delivery, не бесконечное пространство комбинаций.
- TC12 — public: новые блоки каждого профиля, profile/chain admission, delivery и reconstruction; сверка headers/receipts с native источником, управляемый testnet corpus. Public smoke не доказывает полный trace oracle и не заменяет локальную матрицу.

Каждый единичный обязательный fault boundary выполняется на каждом применимом профиле. Минимальные составные сценарии: reorg+restart, partial publish+lost ACK+Gateway restart, backlog+drain, fork transition+restart, profile isolation+один недоступный supporting service. Остальные сочетания — документированный pairwise план и seeded exploration. Полный перебор неограниченных сочетаний/состояний не обещается.

## Reader и независимая проверка

Reader имеет собственные test-only credentials/consumer и читает реальные сообщения NATS. Он проверяет wire/schema/IDs/digests, собирает transport parts и RecordFragments в записи и batches, учитывает exact duplicates и принятые lifecycle revisions. Отсутствующие и неожиданные записи сверяются с полным expected набором, а не только с количеством сообщений. Из больших blobs не строится неограниченный RAM объект: сборка/сравнение допускают bounded disk spool.

Logs identify profile/run/case, block/transaction/event IDs, processing stage, and the reason for PASS/FAIL. Preserve complete frames/records, manifests, expected/actual differences, and diagnostics as hashed artifacts without secrets. Correlate durable producer PubAck evidence separately from consumer ACK. D87 below specifies finite source, delivery, and stream boundaries, full comparison, and reorg handling. Quiet periods and deadlines do not prove completeness.

Expected semantic outcomes получены из native receipts/state commitments плюс независимый manually checkable/reference execution scenario. Тот же normalizer не генерирует эталон для себя. Источник расхождения (producer/transport/reconstruction/oracle) отражается в отчёте; подозрение на oracle не превращает FAIL в PASS.

## Матрица и приёмка

Evidence schema D82: CaseRegistry/CaseResult/RunManifest schema_version=3. Это версия тестовых доказательств: logical/wire/storage schemas продукта не меняются. Уникальная case identity — `(ac_id, network, profile, profile_manifest_digest, fork_variant, fixture_kind, suite, variant_id)`. Fields `task_id`, fixture id/version и rules сохраняются. DOC имеет profile=`DOC`, digest/fork=`NOT_APPLICABLE`, fixture_kind=`document`, но никогда не runtime PASS. ALL разворачивается во все семь профилей; ETH/BSC/POLY — во все профили семейства. COMMON runtime cases всё равно получают применимые profile variants; общая реализация не означает общий PASS. Не поддержанный fork не включается как runtime-supported и получает подтверждённое scope rule, не скрытый пропуск.

RunManifest дополнительно сохраняет profile manifest digest, fixture_kind, suite, resource/deadline manifest digest, фактические времена фаз/лимиты, точные case identities и output hashes. Для multi-profile orchestration создаётся parent manifest, отдельные child manifests каждого профиля и отдельный integration outcome для TC08. PASS общего запуска не закрывает missing child. Составной scenario имеет единый correlation ID без смешения сетевых identities. v2 evidence остаётся историческим; переименованием полей runtime PASS не переносится.

Applicability/verdict остаются раздельными по IMPLEMENTATION_GATES: APPLICABLE+NOT_RUN/PASS/FAIL; NOT_APPLICABLE, NOT_ENABLED, DEFERRED только с разрешённым rule_ref/reason и без выдуманного запуска. Недоступный testnet, нехватка средств, несовместимая сборка и отсутствие fixtures — препятствия выполнению, не основание N/A обязательного профиля. Требуемые cases всех suites должны иметь валидный PASS; стадии принимают только свой subset. Quick PASS обозначается только quick PASS.

Изменение реестра профилей/AC/variants/fork/client/config/schema/fixture/oracle/deadline обновляет digest и инвалидирует затронутые results. Добавленный профиль получает все общие cases; добавленный case — все применимые профили. Gate отвергает duplicate/missing/unknown identity, неподтверждённое исключение, устаревшее evidence и любой обязательный NOT_RUN/FAIL. Summary показывает знаменатель applicable, PASS/FAIL/NOT_RUN и исключения отдельно по каждому профилю, fork, suite и case. Нельзя заменить полноту процентом без перечисления остатка.

## D87 — Finite reader completion

D87 resolves the design of TEST-OPEN-01 under D84. BOOT-07 requires independent acceptance of this contract before the item is closed. This is a test-only observation protocol; it adds no product event, RPC, CLI mode, YAML key, or delivery guarantee. The existing native decision bridge, shutdown/drain protocol, and JetStream management interface supply the boundaries. TEST-OPEN-02 still owns the independent corpus and minimum quotas. Document acceptance is not runtime PASS.

### Freeze the plan and the evidence

Before READY, the versioned RunPlan fixes the profiles, cases, source start conditions, finite stop trigger, scenario actions, required quotas, expected-result rules, allowed faults, and phase deadlines. Local runs stop after the declared finite driver actions and native decisions. Public runs stop after the declared observation duration and/or native-decision quota; the plan states the exact AND/OR rule. A testnet plan also requires its controlled transactions to reach their declared inclusion/outcome conditions. A failed or unmet condition cannot be replaced after the run with a smaller window. A quota is a coverage condition, not a proof of transport completeness. Mainnet remains passive.

Each profile uses isolated test stores, credentials, and destination streams. Before admission, record the native live boundary H/hash, network identity, native store identity and decision frontier, producer/run identities, binding/admission generations, and each stream's identity, configuration, and lower sequence L. A new empty stream uses L=0. Any seeded history or retained activation references must have an explicit, hash-bound baseline, including the bytes and lifecycle references needed by the expected result. A reader cannot infer absent history from the new stream. Fixture preparation and the baseline cannot satisfy actions that must occur during the measured run.

The harness preserves three separate append-only evidence sets with bounded disk storage: source admissions/authoritative native decisions and consumed inputs; producer/Gateway intents, immutable manifests/plans and durable acknowledgments; and actual JetStream messages with stream sequence, subject, headers, and payload bytes. Capture source evidence at the existing admission/decision boundaries before cleanup can remove markers or pins. It must identify in-flight admissions and no-public-event decisions as well as public transitions. Capture durable delivery evidence before its normal cleanup. These are test observations of existing state, not extra production obligations. Missing, conflicting, or incomplete evidence prevents PASS.

The source ledger is independent of normalized output: it records native identities, inputs, authoritative old/new heads and finality evidence, and native decision order, not a copy of the event list emitted by the normalizer. Reconcile it against the driver actions and native commitments using the registered oracle. Product markers alone do not prove that every required source action was observed. Public expected values may be materialized after the window from preserved native data, but the rules and input provenance are fixed before the run and cannot be inferred from received normalized records. The independent oracle must cover the entire realized window; unknown results are not assumed correct. BOOT-08 supplies concrete oracles/corpus, including exact fees and lifecycle effects.

### Close source and delivery boundaries

When the stop trigger is met, stop further driver actions and stop LIVE using the existing shutdown procedure. A requested stop time, block height, transaction receipt, or quiet interval is not the actual cutoff. Confirm that the old writer has exited, then run the same compatible binary in the existing drain mode with the same stores/binding. Include every admission already durably accepted, every transition that actually committed before shutdown, and all recovery/lifecycle obligations that drain must resolve. Preserve their actual native order. No new live H+1 capture is allowed during drain.

The source end boundary is the terminal decision frontier after those obligations resolve, with all admitted observations classified as committed, rejected, or still unresolved. Still unresolved means the boundary did not close. An execution rejected by native rules does not acquire an invented Applied event. Every native decision with public events maps to one whole delivery batch; a decision without public events has a durable checkpoint and no batch. Preserve the complete multi-block reorg or finality-only decision. Never cut a batch at a block height or discard late fragments because the stop was requested earlier. Include any extra committed decisions from the stop race in the realized window; they cannot repair a missing planned action.

Require durable DRAINED and the matching SealAck, drain_id, highwater, generations, retired prefixes, and resolved release obligations for every producer/Gateway pair. The sealed highwater must account for every delivery intent allocated in that episode, including recovered work. Cross-check its manifests against the independent source-derived event set; a producer that omitted a whole batch must not pass by sealing a smaller set. Event_sequence gaps from abandoned staging are legal; batch obligations cannot be silently skipped. Retained recovery-state waiting for finality does not prevent closure when the existing drain contract permits it.

A restart/recovery/cutover scenario may contain several LIVE episodes. The manifest records every episode and accepted Resume/Switch boundary in order; the final closure covers their union. Do not resume after the final drain in this run. Keep every destination touched by the scenario and verify each separately. A post-cutover Removed/Status may reference Applied in the old destination or explicit baseline; this does not require history copying or a self-contained new stream.

### Close the JetStream boundary and read the full interval

Successful-delivery runs use test streams with LimitsPolicy, no expiration within the evidence lifetime, and capacity reserved for the plan. Configure limits to reject new publications instead of evicting existing messages. Consumer ACK must not remove stream data. Disable rollup, message expiration features, and unplanned deletion/purge; restrict stream-management credentials to the harness. Preserve configuration and identity evidence throughout the run. Expiry, deletion, purge, stream recreation, or an unexplained sequence gap prevents successful transport proof even when expected logical records happen to be present. A planned temporary publication rejection can pass only after the declared recovery and complete delivery. An unexpected application rejection is a scenario failure; the narrowly defined fence-induced exact retry below is a separate closure diagnostic. Scope publisher permissions to the declared test destinations and retain rejected extra publication attempts as evidence.

After all final drains, stop Gateway publication workers and close their connections. Preserve an exhaustive test-only census of publication attempts at the harness-controlled NATS ingress, including full immutable request bytes, connection/frame ordinal, reply correlation, and observed server responses. The observation point must precede injected reply loss and cover every permitted publisher path. It adds no product header or message. Classify each attempt as server-acknowledged, definitively rejected without append, not forwarded, or outcome unknown. A client timeout, cancellation, socket close, flush/PING response, or the acknowledgment of another retry does not resolve the earlier attempt at the server. Pending or unknown attempts require the terminal fence below; do not silently discard them.

A JetStream seal acknowledgment is an admission/configuration change, not sufficient proof that previously admitted clustered writes have finished. The harness seals only its isolated test streams after required recovery/resume/cutover actions. Then apply the default terminal fence: stop every NATS process in the isolated topology, confirm all old process instances have exited, preserve their exact stores and identities, and restart the same pinned topology with all product publishing ingress disabled from startup. Disable every other source of stream writes, including external routes/leaf connections, sources/mirrors, scheduling, rollup, and expiration. Permit only the test reader and read/monitoring management operations; no stream replacement, purge, or writable restore is allowed. The stop/restart and recovery are measured run phases, not preparation. An old process or delayed transport connection that could still publish invalidates the fence.

For standalone NATS, require successful native store recovery and stream readiness with the sealed configuration and original identity before sampling U. For clustered NATS, also require the unchanged membership and all configured voting replicas to recover. For each relevant stream Raft group, collect source-verified monitoring evidence from every replica: the same leader and term, no catch-up/error/paused state, empty proposal/entry/apply work queues, and equality of the last log index, committed index, and applied index at a common recovered frontier. Only an exact-lock fence implementation whose source review proves these fields cover the complete apply path may use them; response-queue emptiness or a healthy HTTP endpoint alone does not establish the frontier. All old in-memory handlers have ended at the process fence, all surviving log work has applied, and no new data-producing ingress exists. A leadership/membership change or new log work during evidence collection invalidates that sample and requires a fresh complete sample within the deadline.

Read terminal stream information and upper sequence U only after that fence. Recheck the stream identity/configuration and retain the isolated topology and stores until raw evidence is exported and checked. A stream-sequence increase after U invalidates the fence and the case; never silently move U or ignore a later append. Resolve previously unknown attempts against the fenced store and the ingress census: an already committed append is included in (L,U], while an uncommitted old attempt can no longer append. Required parts still need their own durable producer delivery proof. Every extra or altered attempt fails the declared output contract even if shutdown prevented its append. Matching logical counts cannot replace the census or terminal stream coverage.

RunPlan identifies the terminal-fence implementation, exact NATS source/build/configuration, topology, and its prior conformance evidence. E01 must test the standalone and each enabled clustered path, including a publish paused after the pre-seal check but before proposal, a delayed committed apply, a lost acknowledgment, and a leader change during closure. A version/topology change invalidates this evidence. If the exact lock lacks the required observations or the fence cannot be proved, preparation rejects that configuration; if a started run cannot establish it by the deadline, the case is FAIL. Do not substitute a quiet interval, repeated unchanged stream info, a seal response, or an unverified shutdown assumption. This contract defines the fence; it does not claim that any candidate NATS build has passed it.

A late attempt rejected solely because of this test fence is a permitted closure diagnostic only when its bytes/identity exactly match a previously acknowledged required part whose stored bytes are included in the verified interval or declared baseline. It adds no missing delivery obligation and must be labeled as a fence-induced exact retry, separately from application rejections. A first/unique part, changed bytes, an extra identity, an unproven earlier acknowledgment, or a rejection caused before the fence follows the scenario's ordinary failure/recovery rule. The fence cannot make incomplete drain successful. This exception preserves at-least-once retry behavior without hiding extra output.

The [NATS stream configuration contract](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/streams.md) documents sealing and retention, but does not by itself establish the terminal barrier. At reviewed source commit 5a815f11a911efa2c88fd1dbfb18ed89a449bfc1, [clustered admission](https://github.com/nats-io/nats-server/blob/5a815f11a911efa2c88fd1dbfb18ed89a449bfc1/server/jetstream_cluster.go#L13080) reads the sealed flag before proposal, [clustered apply](https://github.com/nats-io/nats-server/blob/5a815f11a911efa2c88fd1dbfb18ed89a449bfc1/server/stream.go#L6559) skips that standalone consistency check, and [Raft monitoring](https://github.com/nats-io/nats-server/blob/5a815f11a911efa2c88fd1dbfb18ed89a449bfc1/server/monitor.go#L4233) exposes candidate frontier/queue fields. This source review identifies a barrier proof obligation, not a reproduced server defect or an accepted runtime pin.

The independent reader uses its own explicit-ACK consumer, reads all subjects in each test stream from L+1, and preserves every unique stream sequence through U. It can start during LIVE; final verification uses the closed interval. Consumer redelivery of the same sequence must preserve identical bytes. Do not use a subject filter that hides unexpected messages, DeliverLast, a pending-message count, or a consumer ACK floor as the completion test. Every integer stream sequence in (L,U] must be accounted for by a stored message with its full bytes. The empty case U=L is valid only when the independent expected set and delivery evidence also prove no publication obligation. Gap detection is about JetStream stream sequences; native/event counters have their own rules. The existing [NATS consumer contract](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/consumers.md) defines explicit acknowledgments and start-sequence delivery.

Check every message's destination, subject, headers, identities, sizes, and bytes against the immutable publication plan. Collapse exact publication retries by their immutable part identity only after equality checks; retries stored at distinct stream sequences are retained as physical evidence and do not create extra logical events. Reuse of an identity with changed bytes, a new identity for a replayed event, an unexpected generation, or any unplanned message fails comparison. Join producer PubAck evidence to the actual stream and sequence/part; consumer ACK is never producer PubAck. Producer delivery success and readable retained messages are separate facts.

Reconstruct every transport part and typed RecordFragment, then verify fragment order/count, tree/blob structure, complete record seal/digest, full batch manifest, and lifecycle references. Use bounded disk indexes/spools. Seeing the last index, a RecordSeal, one complete event, or all messages currently available does not prove completeness. Compare exact expected and actual logical identity sets and values, including extra and missing records; equal counts are insufficient. No partial record or partial batch is accepted. Unexpected corruption or missing parts fails immediately when proven, otherwise it remains incomplete until the finite deadline.

### Reorgs, outcomes, and deadlines

For local reorg/finality cases, the fixture declares the exact native decision/lifecycle sequence. For public streams, derive that sequence from the independently preserved authoritative decisions inside the closed window. Include all required Applied, Removed, and Status revisions in that order, including reverted branches, handled rollback, and finality-only decisions. A reorg during the shutdown/drain boundary is included if it belongs to an accepted obligation or committed transition. A later public-chain reorg after the closed boundary is outside this run: do not rewrite the expected window, wait for permanent chain stability, or assert that the last Applied remains canonical forever. Finality/pin-cleanup scenarios must meet their own required native/L1 evidence; reader closure does not waive it.

ReaderBoundaryManifest schema_version=1 is a test-only artifact referenced by the existing RunManifest output hashes. It records the RunPlan and oracle references/digests; profile/case identities; each source baseline, admission set and terminal frontier; episode/binding/generation transitions; delivery manifests, highwaters and seal/ack evidence; the publication-attempt census and classifications; stream identities/configuration, L/U and seal evidence; terminal-fence implementation/conformance references, process-instance exits/restarts, ingress restrictions and recovered log frontiers; raw-message coverage/digests; logical expected/actual diffs; phase timestamps/deadlines; and a separate outcome for each of source closure, delivery closure, terminal fence, stream coverage, reconstruction, and semantic comparison. Large sets use hashed chunk artifacts. Distinguish NOT_RUN, satisfied, failed, and incomplete conditions in this artifact; this does not add CaseResult verdicts or change product schemas. The manifest must explain which condition prevented completion.

Reader completion means source and delivery boundaries are closed, all sealed stream intervals have been read and verified, and all records/batches are reconstructed. It does not by itself prove expected semantic results. A successful positive case additionally requires independent exact comparison, required coverage, durable producer delivery proof, and all scenario-specific checks within the deadline. A completed reader with a semantic mismatch yields FAIL. A process exit, timeout, quiet period, or first received message yields no completeness proof.

Startup, observation, shutdown/drain, stream closure, reader reconstruction, and comparison have finite phase deadlines inside D83's measured run. Standard total time remains at most 1800 seconds, including stop races, recovery, spool work, and comparison. The reader may report conclusive failure early and preserve partial artifacts. If any required phase remains incomplete at its deadline after the run starts, the case is FAIL with a timeout stage and missing obligations; the deadline is never a success trigger. Preparation failure remains NOT_RUN with diagnostics. D83's single clean retry is a separate run and window with first_run_id; it cannot merge fragments/evidence with the first attempt or erase that FAIL.

A fault/mutation case may require a specific rejection, blocked state, or timeout. Its expected failure predicate, observation boundary, and deadline must be declared before READY. Stop its writers, seal/read the test streams, and preserve the actual partial delivery/source evidence. Such a case passes only by proving the declared negative behavior and forbidden-output checks; do not label incomplete drain or partial records as successful reader completion. An arbitrary timeout does not satisfy a more specific expected error. Recovered positive-delivery cases still require every positive closure condition.

## D83 — настраиваемый стенд, обновления и повторы

**Конфигурация стенда.** RunPlan выбирает profiles, suite, standard/extended, fixture versions, seed, parallelism, resource limits, число блоков/транзакций/операций, размеры payload/records, длительность outage/soak и фазовые deadlines. Preparation выбирает воспроизводимое локальное состояние либо подготовленные публичные ноды; native-seam, local-e2e и public остаются разными видами evidence. Необязательные реальные supporting services заменяются фиксированными ответами только в явно помеченном seam test. Full E2E не подменяется mock. Настройки не расширяют продуктовый YAML, это отдельный test-only RunPlan.

Acceptance RunPlan разворачивает все назначенные mandatory variants минимум по одному разу; каждый размерный boundary B−1/B/B+1, перечисленный fork и обязательный fault combination сохраняются. Настройка интенсивности добавляет повторения и объём, но не снимает обязательные cases. Уменьшенный набор разрешён как diagnostic: отчёт явно PARTIAL, незапущенные applicable cells NOT_RUN, полного gate PASS нет. Minimum soak quota и число seeds фиксируются в versioned acceptance plan до запуска; понижение плана после FAIL не делает прежний результат успешным. Частные значения corpus/quotas относятся к TEST-OPEN-02; их отсутствие не закрывает приёмку.

**Отдельный version updater.** В поставляемом проекте предусматривается самостоятельный скрипт `scripts/refresh-versions` с режимами `check` и `update`. Это требование к артефакту разработки D84; на момент передачи файл скрипта ещё не создан. Оба режима используют versioned ComponentRegistry с полным перечнем native и supporting clients, NATS, RocksDB/gRPC/Protobuf libraries, toolchains/generators, base images и прямых/транзитивных dependency locks в поставке. Для каждой записи определены официальный источник релизов, канал stable, способ точного pin, dependency/profile constraints и способ проверки. Компонент без источника/правила обновления — явный блокер, а не тихий skip.

`check` читает реестр и официальные источники без изменения активных locks; формирует UpdateReport с current/latest stable/selected candidate, источниками, timestamp, compatibility/security notices и blocked reasons. `update` получает актуальные stable releases, разрешает совместимый набор зависимостей и создаёт отдельный candidate lock с точными versions/commits/image digests/artifact hashes. Floating latest, незакреплённые branches и диапазоны вместо разрешённого lock запрещены; prerelease/nightly автоматически не выбираются. Скрипт не подставляет чужой image/непроверенный artifact при недоступности источника. Недоступный источник означает incomplete check и nonzero exit, не «всё актуально».

The candidate must pass provenance/hash checks, reproducible builds, per-profile native/supporting compatibility, the applicable corpus, and migration-boundary checks. Results from the previous lock do not transfer. Verification may use several runs; the 1800-second limit applies to each standard run. Promote a candidate only after the mandatory gate, including fresh public smoke. Unaccepted BOOT-07/08 decisions or missing runtime evidence block full acceptance. UpdateReport distinguishes a discovered update, a prepared candidate, and an accepted active lock.

Запись активного lock атомарна, с проверкой исходной revision и сохранением прежнего lock/report; конкурентное обновление или сбой не оставляют смешанный набор версий. Скрипт не рестартует production, не меняет пользовательские stores и не выполняет автоматическую миграцию WAL. Для несовместимых persistent formats действует drain старой сборкой по D59; возврат старого lock не обещает downgrade уже изменённого state. Если последняя стабильная версия несовместима с обязательным профилем, прежний активный lock сохраняется, отчёт явно показывает отставание/блокер; нельзя назвать его актуальным. D83 разрешает этот управляемый version-update workflow вместо отдельного интервью о каждом compatible pin; изменение scope/семантики/неподдержанная миграция остаются отдельным решением. По D84 workflow реализуется по назначенным issues с проверками.

**Собственные тестовые контракты.** На каждом поддерживаемом публичном testnet и в local-e2e предусматривается контролируемый corpus собственных контрактов: token transfer/transferFrom/allowance, zero/boundary values, logs/storage, nested call/delegatecall/staticcall, handled/unhandled revert, out-of-gas, CREATE/CREATE2 success/failure и fork-dependent действия. Не универсализировать поведение произвольного ERC-контракта; expected задаётся конкретным исходником и сценарием. Scenario actions выполняются после начала measured run; deployment/funding до run не служат evidence для CREATE/fee cases, которые обязаны выполнить отдельную проверяемую операцию внутри run.

Corpus manifest закрепляет исходники, compiler/settings, bytecode hashes, адрес/chain identity, deployment provenance, calldata, начальное состояние/балансы/allowance, sender/nonce и ожидаемые эффекты. Funding и deployment воспроизводимы; receipts/code проверяются до READY. Signer только testnet, mainnet keys/funding исключены. Контракты тестируют execution cases, но не управляют публичным consensus: reorg, power loss, client failures и fork transitions остаются управляемыми локальными сценариями. Mainnet smoke пассивен; публичный testnet PASS не закрывает профиль mainnet.

Известные токены, например USDT, используются дополнительными закреплёнными transaction fixtures с проверенными network/address/block/tx identity. Сумма перевода сверяется точно с заданным input, logs и применимыми состояниями; для обычного успешного сценария не нужен перебор всех положительных сумм, но zero/boundary/revert — отдельные варианты. Transfer log не является полным oracle trace/state/rollback. Подробный независимый expected corpus разрешено доработать позднее как TEST-OPEN-02; тот же normalizer не генерирует эталон для себя.

**Простая политика повторов.** Первая неудачная попытка сохраняется с FAIL и artifacts. Разрешён ровно один диагностический повтор того же plan/versions/seed на чистом окружении; это новый run_id с first_run_id, attempt_index=2 и retry_reason. Первый run имеет attempt_index=1. Успех повтора отмечается диагностикой UNSTABLE в attempt-group summary, но исходная case acceptance остаётся FAIL; новый verdict enum для CaseResult не вводится. Второй FAIL также оставляет FAIL. Ретраи «до зелёного» запрещены. Отмена/недоступность на preparation дают NOT_RUN с причиной, но не право потерять предшествовавший FAIL.

После устранения причины нужен новый полный успешный run затронутых cases с correction_ref на изменение либо зафиксированное устранение внешней причины; прежние попытки остаются историей. Без исправления один успешный запуск не закрывает нестабильность. Перед приёмкой release candidate выполняется новый public-smoke каждого публичного профиля на точном lock/config/profile revision; historical smoke другого кандидата не переносится. Обязательная недоступная сеть блокирует соответствующий gate, не подменяется локальным PASS. Правила invalidation остальных результатов из D82 сохраняются.

**Testing design status.** D87 specifies TEST-OPEN-01; it closes after independent BOOT-07 acceptance. TEST-OPEN-02 remains open for BOOT-08: the versioned independent corpus and minimum soak/seed quotas. Neither item is a DEFERRED/NOT_APPLICABLE exception for mandatory runtime cases. Documentation and independent review do not execute those cases; runtime remains NOT_RUN until actual evidence exists. D84 delegates decisions within the accepted guarantees; changes to those guarantees require an owner decision. E07/full acceptance remains blocked by any missing required design or runtime evidence.
