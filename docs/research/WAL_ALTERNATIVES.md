# E00-03.06-B: альтернативы RocksDB для локальной очереди

Дата проверки: 2026-10-16. Статус: исследование и предложение; движок не утверждён. SQLite исключён пользователем. Код и нагрузочные тесты не выполнялись.

## Что сравниваем

Не индексатор и не архив блокчейна: локальная очередь готовых protobuf-сообщений и служебного состояния. Один владелец записи на экземпляр, отдельные live/history процессы и тома. Данные сохраняются до PubAck всех сообщений подготовленного блока. После этого payload удаляется; повторная доставка разрешена. Нет TTL и прикладной квоты. Go-компоненты и Rust-компонент Base требуют отдельно оценивать библиотеки и сборку.

Внутренний WAL движка не равен нашей очереди. Pending payload остаётся логически доступным после checkpoint/flush самого движка. Ни один движок не обеспечивает бесконечный физический диск: ошибка записи не может считаться успешным WAL_SAVED.

## Кандидаты

| Кандидат | Проверенные свойства | Вывод для нашей нагрузки |
|---|---|---|
| Pebble | Go LSM, production-использование CockroachDB; batches, sync write options, range deletion | Главная альтернатива для Go. Payload и metadata могут жить в одном KV. Отсутствие C++-сборки упрощает Go-компоненты; compaction и освобождение места после удаления измерять |
| Badger | Go, LSM с отдельным value log, транзакции; управляемый приложением value-log GC | Интересен при крупных payload. Цена — отдельная работа GC и проверка границ транзакций; не считать запись большого WriteBatch одной атомарной операцией |
| MDBX | C, транзакционная copy-on-write KV-модель, один writer, режим durable commit; Go/Rust wrappers существуют | Альтернатива общего движка для двух языков. Один writer нам подходит. Проверить рост/reuse страниц, работу с крупными значениями и стоимость durable commits |
| LMDB | Родственная MDBX модель memory-mapped transactional KV | Не включать отдельным первым POC: преимущества именно над MDBX для этой задачи не установлены; конкретные актуальные Go/Rust bindings не проверены |
| tidwall/wal | Go append log, монотонные индексы, batch, Sync, truncate с начала/конца | Полезен как эксперимент с последовательным журналом. Это не готовая транзакционная очередь: commit-marker, ACK cursor, recovery и согласование metadata остаются нашей задачей |

Это архитектурные выводы, а не рейтинг throughput. Нет оснований заявлять, что кандидат быстрее RocksDB или SQLite на наших данных без одинакового durable режима и измерений.

## Pebble: основной Go-кандидат

README подтверждает production-использование в CockroachDB. Это не экспериментальная библиотека только из-за реализации на Go. При этом Pebble v2 не открывает RocksDB-файлы напрямую: миграцию/совместимость форматов нельзя предполагать. Подтверждённые upstream-материалы: [README](https://github.com/cockroachdb/pebble), [batch.go](https://github.com/cockroachdb/pebble/blob/master/batch.go), [write options](https://github.com/cockroachdb/pebble/blob/master/options.go).

Для POC: хранить сообщения и block manifest в KV, durable batch перед разрешением отправки; удалять подтверждённый блок и менять служебную позицию согласованно. Большой блок не обязан помещаться в один RAM batch: отдельные записи с завершающим marker требуют собственного recovery-контракта.

Нативный поддерживаемый Rust API в просмотренных материалах не найден. Это не доказательство отсутствия сторонних wrappers, но оснований назначать Pebble единым embedded backend Go/Rust сейчас нет. Перенос durable ownership в общий Go-процесс был бы отдельным архитектурным изменением, а не бесплатным свойством движка. Публичные [релизы](https://github.com/cockroachdb/pebble/releases) доступны; точный совместимый tag и toolchain необходимо закрепить перед POC, а не автоматически брать master.

## Badger: большие payload против стоимости GC

Разделение ключей и значений делает Badger интересным для крупных protobuf. Но рекламное сравнение upstream не переносится на наш workload. Основание: [описание архитектуры](https://github.com/dgraph-io/badger).

`SyncWrites` нужно включать для выбранной гарантии durable write; текущий default `false` нельзя принимать как контракт сохранности при потере питания. Источник: [options.go](https://github.com/dgraph-io/badger/blob/main/options.go). Удаление ключей не означает немедленного освобождения value-log файлов: `RunValueLogGC` вызывает приложение, и последнему value-log файлу нужны особые условия ротации/очистки. Источник: [quickstart](https://github.com/dgraph-io/badger/blob/main/docs/quickstart.md).

`WriteBatch` способен последовательно создавать и коммитить несколько транзакций; атомарность всего блока нельзя выводить из названия API. Нужен закрывающий manifest либо ограниченная транзакция и отдельный протокол больших блоков. Источник: [batch.go](https://github.com/dgraph-io/badger/blob/main/batch.go).

Это Go-библиотека; поддерживаемый Rust binding не подтверждён. Даты последних релизов/коммитов и совместимость с нашим toolchain отдельно не валидированы, поэтому утверждения «активнее/надёжнее RocksDB» нет.

## MDBX и LMDB

MDBX имеет одного сериализованного writer; это соответствует выбранному ownership. Durable режим отличается от режимов с ослабленной синхронизацией — нельзя сравнивать их как равную гарантию. Размер/geometry и долгие readers требуют отдельной проверки. Источники: [официальный обзор MDBX](https://libmdbx.dqdkfa.ru/docs/en/deep-dive/architecture.html), [механизмы транзакций](https://libmdbx.dqdkfa.ru/docs/en/textbook/03-tom-iii-mehanizmy.html).

Проверены два конкретных wrappers:

- [erigontech/mdbx-go](https://github.com/erigontech/mdbx-go): Cgo/C-компилятор; README указывает Go 1.25; API geometry и durability. Zero-copy значения живут в пределах допустимого срока транзакции — для асинхронной публикации нужны корректное владение bytes или копирование.
- [vorot93/libmdbx-rs](https://github.com/vorot93/libmdbx-rs): vendored C, C compiler и libclang/bindgen; pre-1.0 API, Rust edition 2024. Версии wrappers и vendored C должны быть проверены и закреплены, не предполагается их бинарная идентичность.

Оба репозитория доступны и описывают требования сборки. Это проверка наличия интеграций, не аудит долгосрочного сопровождения. [VERSION.json Go wrapper](https://github.com/erigontech/mdbx-go/blob/master/libmdbx/VERSION.json) позволяет проверить vendored C перед фиксацией зависимости.

LMDB отдельно не рекомендуется в первый раунд: его конкретные wrappers, актуальные версии и преимущество для очереди крупных сообщений не исследованы достаточно. Нельзя автоматически переносить параметры, shrink/geometry и свойства MDBX на LMDB. Справочная исходная документация: [LMDB](http://www.lmdb.tech/doc/); её доступность/содержимое в этом исследовании не удалось независимо подтвердить, поэтому детальные рекомендации по LMDB не формулируются.

## Сегментный журнал

[tidwall/wal](https://github.com/tidwall/wal) даёт append, batch и усечение по индексам. [Опубликованный API](https://pkg.go.dev/github.com/tidwall/wal) описывает `NoSync=false`, `Sync()` и `TruncateFront`; `AllowEmpty` меняет поведение пустого журнала. Нельзя переносить транзакционные гарантии KV на `WriteBatch` этого log без проверки реализации и crash-тестов.

Наше предложение поверх такого журнала: данные + marker закрытого блока, отдельно безопасно сохранённый ACK cursor, удаление только подтверждённого префикса. Если ACK приходят не по порядку, нельзя перескочить неподтверждённый блок при truncate. Допустимые повторы упрощают recovery, но не разрешают удалять неподтверждённые данные. Для Rust нет проверенного общего backend; maintenance и crash-поведение библиотеки требуют дополнительного аудита. Поэтому это эксперимент второго порядка, не рекомендуемый стартовый стек.

## Что заслуживает POC

1. **RocksDB как основной baseline; Pebble как Go-альтернатива.** Одинаковые protobuf, одинаковый sync-контракт, одинаковый порядок ACK/cleanup. Pebble проверять только в Go-owned store; не менять архитектуру Rust ради сравнительного теста.
2. **MDBX — следующий кандидат**, если важен единый C-движок с двумя языковыми wrappers или измерения покажут неприемлемую стоимость LSM compaction.
3. Badger и сегментный log — только при конкретном ограничении первых кандидатов. Не тратить время на пять одинаковых прототипов заранее.

Измерения: sustained append во время отсутствия NATS; replay накопленного backlog одновременно с новыми блоками; bytes written на payload byte; CPU/RSS; p95/p99 durable commit; фактическое освобождение/reuse диска; recovery time. Обязательные crash-точки: до закрытия batch, после sync, после PubAck до локальной фиксации, во время cleanup; отдельный случай disk-full. Проверяется отсутствие удаления неподтверждённых сообщений и сохранение recovery cursor, а не полнота блокчейна. Сравнение без одинакового durable режима не принимать.
