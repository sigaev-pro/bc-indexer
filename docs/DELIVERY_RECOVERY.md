# E00-03.06 — доставка и восстановление

2026-10-16. Требования D26–D31 приняты. Технический выбор backend остаётся открытым; этот документ не означает начало реализации.

## Граница ответственности

Получение native данных → нормализация → локальный WAL → Gateway сети → NATS JetStream PubAck. Один NATS instance, без проектирования HA и междатацентровой репликации. Для каждого live/history producer отдельное writable состояние. Общий файл embedded DB между pod не используется.

Подтверждение блока означает PubAck всех сообщений и частей закрытого delivery batch, включая block metadata для пустого блока. Batch содержит фактически подготовленные записи; независимая проверка полноты исходного блока исключена D25. ACK транспорта gRPC и успешная запись в socket не заменяют PubAck.

## Порядок работы

1. Принять блок и нормализовать данные. RECEIVED сам по себе не гарантирует сохранность.
2. Сохранить immutable сообщения/части и закрытый список references в WAL. Только после durable commit/flush присвоить WAL_SAVED. Точная реализация транзакции выбирается в оставшейся части .06.
3. Публиковать через Gateway. При временной ошибке повторять с задержкой, не ограничивая число попыток; ID, bytes и part layout при retry сохраняются. Повторы допустимы.
4. Gateway учитывает PubAck каждого сообщения/части. Завершение блока возможно только после ACK всего batch; затем подтверждение возвращается producer.
5. Перед удалением payload зафиксировать restart checkpoint. Удалять только подтверждённые batch; незавершённые сохранять. Минимальное рабочее состояние должно позволять продолжить pending batch и активный N–M, но архив доставленных блоков не нужен.

Рекомендация реализации: удалять payload и обновлять checkpoint одной транзакцией embedded backend либо эквивалентным crash-safe протоколом. Это технический проект, не уже реализованная гарантия.

## Сценарии

| Событие | Требуемое поведение |
|---|---|
| Restart pod, диск сохранён | Восстановить pending WAL и исходный диапазон history; автоматически продолжить |
| Потерян PubAck или ответ Gateway | Повторить отправку; дубли разрешены; не удалять неподтверждённые записи |
| Подтверждены лишь некоторые части | Хранить данные до подтверждения всего batch |
| Crash после ACK, до checkpoint/очистки | Допустима повторная отправка; потеря pending данных недопустима |
| Полная потеря диска | Новый запуск, пользователь повторно задаёт историю N–M; backup/автовосстановление не требуются |
| NATS временно недоступен | Продолжать собирать в WAL без TTL и прикладного лимита; повторять публикацию |
| Физическая ошибка записи/диск заполнен | Явная ошибка; не присваивать WAL_SAVED, не продвигать durable cursor и не удалять накопленное. Это физическая невозможность записи, а не штатная остановка по квоте |
| Все сообщения блока подтверждены | Очистить payload/части и временные статусы; не хранить их дополнительно ради аудита |

Память и число параллельных запросов должны оставаться ограниченными: отсутствие дисковой квоты WAL не означает загрузку всей очереди в RAM. Отставание публикации не приостанавливает сбор при наличии доступного диска.

## Хранение и NATS

Сохраняются только pending данные и минимальное рабочее состояние: cursor, параметры активного job, идентификаторы и сведения, необходимые для retry/возобновления. Доставленные статусы не превращаются в постоянный per-block архив. Технический порядок уборки журналов producer/Gateway должен выдерживать потерю ACK; повторы позволяют обойтись без постоянного dedup registry.

Текущая топология NATS: один instance, одна replica stream. Доступность предполагается, но каждая отправка всё равно ждёт реальный PubAck. После подтверждённой передачи хранение/удаление на стороне NATS и downstream не является гарантией сборщика. Этот этап не задаёт consumer policy или архив транзакций. Конкретные deployment defaults нельзя выдавать за согласованный срок хранения.
