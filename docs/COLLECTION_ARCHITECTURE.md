# Архитектура сбора и публикации в NATS

> D43: полная компоновка и настройка execution/consensus/supporting-компонентов нод, адаптеров, собственных WAL/Gateway и NATS в Docker Compose/Kubernetes входит в задачу. Готовая внешняя нода не является обязательной предпосылкой. Процессы запускает оркестратор по подготовленным проектом конфигурациям; extractor не управляет его API. Детали и открытые решения: [NODE_DEPLOYMENT_SPEC](NODE_DEPLOYMENT_SPEC.md).

> D40: каждая сеть владеет отдельными RocksDB WAL адаптера и журналом Gateway, процессами и прогрессом. Общий multi-network WAL, writer или координатор запрещён. Общий NATS — ранее принятая транспортная инфраструктура; его недоступность обрабатывается независимым накоплением WAL каждой сети. Performance требования и production-методика вне scope.

> D39: native ноду запускает окружение, встроенный адаптер получает YAML при запуске. После синхронизации фиксируется каноническая голова H; live начинается с H+1, pending WAL доставляется независимо. Подписка и фиксация H согласуются без потери новых наблюдений. [Текущий контракт](LIVE_CONFIG_SPEC.md); CFG-S05 завершён как сверка документации, реализация не выполнялась.

> D38 (2026-10-21): загрузка истории и пропусков отложена. History N–M, replay диапазонов и history recovery ниже — будущий контекст, не требования текущего этапа. Сейчас только live-сбор, единая типизированная нормализация и доставка в NATS. Восстановление pending WAL и live reorg/finality сохраняются.

> D36/D37 (2026-10-21): основной сервис только live; история — отдельный сервис на узле native ноды, запускаемый командой N–M. Автоматический поиск и догрузка пропусков после остановки, учёт запусков и внешняя проверка полноты не входят в текущую задачу. Повторная доставка pending WAL сохраняется. Результат — данные в едином строго типизированном формате в NATS; downstream не проектируется. Актуальный контракт управления: [CONFIG_CONTRACT](CONFIG_CONTRACT.md).

> Актуальная граница D23–D25 (2026-10-16): live и history работают в разных pod/process; история запускается простой командой N–M. Пересечения и повторные загрузки допускают дубли. Дедупликация и независимая проверка полноты блока выполняются за пределами сборщика. Здесь проверяется доставка подготовленных сообщений: RECEIVED → WAL_SAVED → NATS_ACKED. BlockComplete/coverage report и общий координатор устранения overlap не требуются. Подробности: [LIVE_HISTORY_DELIVERY](LIVE_HISTORY_DELIVERY.md).

2026-10-15. D16 задаёт границу, D17–D19 фиксируют типизацию, части и топологию; D20 откладывает управление историей. Детальное ТЗ — [v3](../evm-transaction-extractor-tz-v3-codex.md), задачи — [план](DEVELOPMENT_PLAN.md), решения — [журнал](DECISIONS.md).

## Результат

Данные блокчейнов собраны, нормализованы и опубликованы в кластер NATS.IO. Последующие передача, обработка и хранение не проектируются. Сейчас результат работы — согласованное ТЗ; разработка кода ещё не начата.

Сети первого контура: Ethereum Mainnet, BSC Mainnet, Base Mainnet, Arbitrum One, Polygon PoS. Каждая сеть имеет независимый процесс и конфигурацию; изменение одной не требует перезапуска остальных.

Матрица клиентов и concrete source pins проверена в E00-13: [CLIENT_MATRIX.md](CLIENT_MATRIX.md). Рекомендуемый набор — Go Geth/BSC/Nitro/Bor, Rust Base; сопутствующие consensus/runtime компоненты остаются внутри соответствующего профиля сети. Это source-verified стек-кандидат; сборки и capture fixtures ещё не выполнены.

## Путь данных

Native node/executor → Adapter + Native lifecycle bridge → локальный WAL → gRPC → Gateway/publisher → NATS JetStream.

| Узел | Ответственность | Стек и статус |
|---|---|---|
| Native node/executor | Родное исполнение live/import и истории, receipts, состояние, canonical/finality notifications | Клиенты/commits проверены по исходникам в CLIENT_MATRIX; native executor каждой сети, runtime-доказательство в E01 |
| Adapter | Все транзакции, calls/logs/state changes и транзакционные balance actions; нормализация | Go для Geth/BSC/Nitro/Bor, Rust для Base; Classic — отдельный Go native reader + C++ AVM observer, требующий POC; pins и условия в CLIENT_MATRIX |
| Native lifecycle bridge | Отличает speculative execution от canonical inclusion, назначает lifecycle/порядок в пределах producer/run; не устраняет пересечения history/live | Модуль каждого producer/run; logical ownership определён в STATE_OWNERSHIP, durable RocksDB/atomicity — ROCKSDB_DELIVERY_PROTOCOL |
| WAL | Сохраняет нормализованные записи и прогресс до подтверждения публикации | RocksDB 10.4.2, sync WriteBatch; pins и cleanup в [протоколе](ROCKSDB_DELIVERY_PROTOCOL.md) |
| gRPC | Передача нормализованной записи адаптер → Gateway | Protobuf/gRPC — базовый контур; UDS локально или TCP с mTLS между хостами |
| Gateway/publisher | Проверяет схему и целостность, ведёт publication journal, повторяет отправку, назначает publication order | Baseline E00-03.03: Go, gRPC-Go, nats.go; версии в COMPONENT_STACK, один активный издатель сети |
| NATS JetStream | Принимает и подтверждает публикации | D22: внутри Kubernetes/Compose; официальный chart/image baseline. Один NATS, file stream replicas=1; post-ACK retention вне scope |

Принято D19: свой native node/adapter, Gateway, WAL, журнал публикации и лимиты каждой сети; общий NATS с раздельными streams/subjects. Нет вызовов между сборщиками, общего процесса конфигурации или ожидания прогресса соседней сети. Сбой, restart и backfill одной сети не блокируют остальные. Служебное состояние и прогресс изолированы; требования производительности и нагрузочные проверки вне текущего ТЗ (D40). Отказ общего NATS остаётся общим инфраструктурным событием.

## Нормализация

Единые network/block/transaction identities; полные transaction/receipt/log/call данные; точные значения без float; native order; причины изменений балансов и rollback; typed extensions для сетевых отличий. Нормализация не подменяет родное исполнение, не добавляет выдуманные транзакции и не сокращает детали.

Принято D18: одна обычная транзакция — одно сообщение; превышающая лимит — несколько частей с общим event_id, part_index, part_count и digest. E00-14 описывает [логический контракт](MESSAGE_CONTRACT.md): TransportFrame с CompleteRecord либо RecordPart; digest исходных неизменяемых bytes, отдельная blockchain chronology и delivery sequence. Лимиты и компилируемая wire schema ещё не утверждены. Обрезать данные нельзя.

Принято D17: общий строго типизированный контракт для всех поддерживаемых семейств. Обязательны транзакционные, block metadata и reorg/finality сообщения. Системные изменения балансов вне транзакций — необязательное расширение; если оно существенно усложняет код, его можно не реализовывать, явно объявив границу покрытия. Родные системные транзакции и все их эффекты остаются обязательными.

Общий контракт не означает обещания поддержки всех существующих блокчейнов. Первая поставка охватывает три сети по D42 (Ethereum, BSC, Polygon); новые семейства добавляют типизированные профили, сохраняя общие значения полей. Неприменимость поля отличается от отсутствия обязательных данных. Произвольный JSON или невалидируемые opaque extensions не заменяют схему.

Все успешные и неуспешные транзакции в блоках, включая нативные системные типы, сверяются с полным составом блока по hash/index/type/count. Internal calls остаются деталями родительской транзакции; mempool не входит в прежнюю границу. Для неизвестного типа запрещено молча пропускать запись или объявлять блок полным.

## Live и история

D36: основной загрузчик только live. Любая запрошенная история выполняется отдельным сервисом на том же узле, что и нода, по команде N–M. Авто-bootstrap/default три часа/YAML-triggered history отменены. Интерфейс одинаков для сетей, native реализация различается, Kubernetes API не требуется. Другие компоненты не переконфигурируются. [Конфигурация/restart](CONFIG_CONTRACT.md).

Принят отдельный pod/process history worker с native executor/state и лимитами ресурсов; live имеет приоритет. Доступ к историческому состоянию, pruning и воспроизводимость проверяются для каждой сети. Очередь сама по себе не обеспечивает изоляцию CPU/диска. Publication order не равен порядку блокчейна: history может поступать после более новых live-блоков.

## Граница подтверждения и приёмки

Граница доставки: Gateway выдаёт IngestAck только после PubAck всех сообщений/частей закрытого block batch; ACK отдельной записи не разрешает очистить блок. Повторы возможны, идентичности стабильны (at-least-once). D26–D33 и .06 фиксируют накопление без TTL/квоты до ACK и RocksDB recovery; post-ACK retention/HA вне scope. Точный [протокол](ROCKSDB_DELIVERY_PROTOCOL.md).

Приёмочный считыватель проверяет сообщения в NATS по native fixtures всех трёх сетей: поля, действия, порядок, целостность частей, reorg/finality, повторы и подтверждения доставки подготовленных сообщений. Это функциональный тест, не промышленный компонент последующей обработки и не методика production-тестирования. Требования задержки/производительности исключены D40.
