# Последовательность разработки и задачи

> D26–D31 (2026-10-16): [текущие требования доставки и восстановления](DELIVERY_RECOVERY.md). Restart с сохранённым диском автоматический; после потери диска история задаётся заново N–M. WAL копится без TTL/прикладной квоты до подтверждения NATS всех сообщений/частей блока. После ACK payload и временные статусы очищаются; остаётся минимальное рабочее состояние для restart. Сейчас один NATS; HA/backup и дальнейшая судьба подтверждённых данных вне scope. Backend и crash-safe протокол остаются техническими задачами .06.

Статус: каркас разработки в границе D16 с решениями D17–D20 — сбор, нормализация, NATS.IO. Сейчас финализируется архитектурное ТЗ; реализация не начата. Стек закрепляется после проверки клиентов. Обновлено: 2026-10-15.
Текущие решения: [DECISIONS.md](DECISIONS.md). Точка продолжения: [PROJECT_STATUS.md](../PROJECT_STATUS.md).

## Правила выполнения

Пока открыт R01, выполняется только E00. Остальные этапы описывают предлагаемую последовательность и будут уточнены по ответам. Версии клиента, библиотек, runtime, хранилищ и инфраструктуры нельзя выбирать по наличию на машине.

Каждая задача имеет постоянный ID. Статусы: TODO, IN_PROGRESS, BLOCKED, DONE. По умолчанию все незавершённые задачи ниже — TODO; таблица активных задач содержит исключения. DONE требует указанного артефакта и результата проверки. Перед началом задачи записать ID в PROJECT_STATUS.md; после завершения отметить checkbox, сохранить evidence и следующую задачу.

Крупную задачу перед исполнением разбивать на подзадачи с суффиксами .1, .2 и отдельными критериями; уже присвоенные ID не переиспользовать. Коммиты, публикации и деплой фиксировать только после фактического выполнения с hash/URL и результатом проверки. Сохранение файлов не означает наличие удалённой резервной копии.

## Предлагаемая последовательность

E00 Решения → E01 Проверка нативного захвата всех пяти сетей → E02 Общий контракт на примерах всех пяти сетей → E03 Надёжная сквозная доставка → E04 Полный capture пяти сетей → E05 Каноничность и восстановление каждой сети → E06 История и доставка каждой сети → E07 Приёмка первого контура из пяти сетей → E08 Другие сети.

Принято D16: конечный результат — унифицированные сообщения в NATS.IO. Последующая обработка исключена из этапов, стека и приёмки. Проверяющий считыватель — только тестовый инструмент.

Приняты D10–D12 с уточнением D16: ограниченная история + live без полного snapshot адресов; хронологические связи и детали в сообщениях; open-source и пользовательские .yml. Лицензия и YAML schema ещё выбираются.

Принято D05: первый контур — Ethereum, BSC, Base, Arbitrum, Polygon. Предыдущая рекомендация довести до поставки одну Ethereum-сеть, затем переносить остальные, отклонена. Способы интеграции всех пяти сетей проверяются в E01 до утверждения общей схемы E02. Это не определяет число параллельных исполнителей или серверов.

Задачи, зависящие от клиента, выполняются отдельно для каждой из пяти сетей. Для E01-01…04, E04-01…04, E05-01…04 и E06-01…05 конкретные подзадачи имеют суффиксы .ETH, .BSC, .BASE, .ARB, .POLY; родительская задача закрывается только после всех пяти. Команды, commits, evidence и пробелы хранятся раздельно. Приняты Ethereum Mainnet, BSC Mainnet, Base Mainnet, Arbitrum One и Polygon PoS.

Приняты D14/D15/D19: отдельный native node/adapter/WAL/Gateway каждой сети, общий NATS с изолированными streams/subjects и лимитами. Live и команда N–M сохранены; управление YAML/history отложено пользователем D20.

Принято D06: default при старте — последние три часа либо стартовый блок из YAML; live одновременно. Ранее принятый reload с автоматической догрузкой требует согласования с новой командой N–M в JOB-01; до ответа критерий приёмки reload не финализирован. Принято D08: восстановление запуском с тем же YAML; источники и сроки восстановления обсуждаются отдельным пулом REC до выбора соответствующего storage. Автоматический HA пока не принят.

## E01 — воспроизводимая сборка и доказательство захвата

Зависимости: E00; для всех пяти сетей определены варианты сети, кандидаты клиентов и границы прототипов. Стек: родной клиент и его язык для каждой сети. Минимальный тестовый execution harness, затем реальный client import path. Один общий Ethereum-прототип не закрывает E01.

- [ ] E01-01 Закрепить исходники, toolchain и способ интеграции; настроить воспроизводимую сборку. Готово: чистая сборка, versions/commit и точная команда сохранены.
- [ ] E01-02 Составить карту транзакционных capture paths, state mutations и canonical notifications. Готово: все родные типы транзакций и обязательные поля имеют источник; изменения вне транзакций учитываются отдельно как optional.
- [ ] E01-03 Захватить transfer, nested call/revert, fee effects, родные системные транзакции и пустой блок. Готово: полные tx records/before/after сверены с независимым результатом. Вне-транзакционные начисления проверяются только при реализации расширения.
- [ ] E01-04 Проверить стабильные границы операций и повтор исполнения одного fixture. Готово: воспроизводимые результаты/позиции; ранний overhead измерен, ограничения записаны.

- [ ] E01-05 Проверить извлечение поддержанных native типов на fixtures всех пяти сетей, включая failed/system и исторические переходы. Неизвестный тип даёт явную ошибку. Независимый production verifier состава каждого блока не требуется (D25).

Уточнение E00-15 для E01/E02/E04/E06: Arbitrum Classic проверяется как отдельный runtime той же сети, с исходным AVM result inventory и сверкой Ethereum projection; Nitro imported bodies не заменяют execution. Требуется доказать неизменность machine hash/gas/logs/sends при добавлении наблюдения, а также полноту actions/state diff. Для Polygon отдельно проверить legacy receipt/source-only scope, отсутствие ложных system-success/empty выводов, реальные native inputs и переход к body 0x7f. Детальные fixtures: [Classic](research/ARBITRUM_CLASSIC_CAPTURE.md) и [Polygon legacy](research/POLYGON_LEGACY_CAPTURE.md). Пока они не пройдены, полного исторического runtime-покрытия не заявлять.

Gate: если обязательный путь не наблюдаем, доработка интеграции или пересмотр клиента предшествуют созданию универсального production capture. Неполный POC не объявляется полной поддержкой сети.

## E04 — полная транзакционная и балансовая семантика пяти сетей

Зависимости: E03. Стек: native hooks/journal/state APIs закреплённых клиентов, общий transport E03 и необходимые каждой сети consensus/derivation компоненты. Каждая задача имеет пять сетевых подзадач.

- [ ] E04-01 Покрыть call tree, receipt/logs, create/selfdestruct, precompiles, authorization и rollback в согласованном fork profile. Готово: обязательные native fixtures проходят.
- [ ] E04-02 OPTIONAL по D17: оценить и при приемлемой сложности покрыть изменения балансов вне транзакций. Готово для включённого расширения: каталог paths и причин, сверка и отсутствие дублей tx/system. Допустимо NOT_IMPLEMENTED с явным scope; не блокирует основную поставку.
- [ ] E04-03 Проверить нормализацию balance actions, before/after и нулевых суммарных эффектов на выбранных native fixtures. Это тесты разработки, не production balance oracle.
- [ ] E04-04 Проверить реальный live/import path и ограничение работы hooks. Готово: сеть/диск транспорта не выполняются внутри VM hooks; перегрузка останавливает продвижение в определённой точке.

Gate: отсутствие необъяснённых capture gaps на выбранном контрольном диапазоне. Coverage всех исторических версий ещё не подразумевается.

## E05 — каноничность, reorg, finality и restart

Зависимости: E04 и durable guarantees E03. Стек: native notifications + Coordinator + выбранный журнал состояния.

- [ ] E05-01 Реализовать canonical activation registry и финальные статусы. Готово: speculative capture не публикуется как canonical; статусы привязаны к правильной активации.
- [ ] E05-02 Реализовать rollback/reapply транзакций и блоков. Готово: reinclusion и возврат ветки дают корректные активации. Системные события включаются в проверку только при реализации optional расширения.
- [ ] E05-03 Закрыть crash window между нодой, WAL и publication journal согласно REC. При недоступных данных показывать явную ошибку; не объявлять успешную доставку.
- [ ] E05-04 Проверить fencing и конкурентные источники. Готово: старый writer не публикует после смены; гонки capture/reorg/publish/status покрыты тестами выбранной топологии.

Gate: выполнена матрица crash/reorg/finality без необнаруженных пропусков; повторы не создают ложных канонических активаций.

## E06 — историческая выгрузка и учёт доставки

Зависимости: E05, наличие native state перед диапазоном. Стек: native executor, отдельный history pod/process, WAL и локальный журнал доставки; backend выбирается в E00-03.06/REC. Никакого общего overlap coordinator, coverage report или UI.

- [ ] E06-01 Подготовить закреплённый диапазон, стартовое состояние и проверку исторических VM/forks. Готово: источники доступны и воспроизводимы; pruning не уничтожает необходимые данные.
- [ ] E06-02 Реализовать последовательный replay с checkpoints. Готово: остановка/продолжение не требуют независимого полного восстановления state для каждой транзакции.
- [ ] E06-03 Проверить допустимые пересечения live/history и повторные команды. Разные run_id могут публиковать одинаковые блоки; publication order отделён от native execution order. Дедупликация вне scope (D24).
- [x] E06-04 REMOVED_BY_D25: coverage report и независимая проверка полноты диапазона исключены из сборщика. ID сохранён для истории решений; не является незавершённой задачей поставки.
- [ ] E06-05 Пройти тестовые диапазоны всех пяти сетей. Сохранить границы N–M, ошибки, время/ресурсы и статусы доставки; не выдавать результат за доказательство полноты данных блока.
- [ ] E06-06 Реализовать вычисление стартового блока последних трёх часов по timestamps. Готово: проверены пропуски блоков, молодая сеть и неактуальная голова; фиксированное число блоков не подменяет время.
- [ ] E06-07 Реализовать применение YAML выбранного процесса сети по ответу JOB-01. Готово: связь со стартовой историей и командой N–M однозначна, live продолжается, invalid config обработан явно; других сетей изменение не касается.
- [ ] E06-08 Проверить сохранение служебного прогресса при reload/restart по CFG/REC. История доставки не используется для устранения пересечений или запрета повторной команды.
- [ ] E06-09 Проверить сценарии конечного пользователя через .yml. Готово: выбранный поднабор сетей запускается без правки кода; default 3 часа, короткая dev-история и production from-block работают; live дополняет историю без автоматического удаления по возрасту.
- [ ] E06-10 Реализовать простую команду history --config network.yml --from N --to M: отдельный pod/Job или Compose process, включительные границы, конечный run_id, результат доставки. Без UI и постоянного management API.
- [ ] E06-11 Проверить параллельный live и отдельный history pod: live продолжает работу, лимиты ресурсов соблюдены, native state доступен; пересечения и повторы разрешены.
- [ ] E06-12 Реализовать локальный журнал RECEIVED → WAL_SAVED → NATS_ACKED по выбранному в .06/REC backend. Ключ включает network/producer/run/block hash; успех требует PubAck всех подготовленных сообщений и частей. Известные ошибки сохраняются; журнал не устраняет повторы и не доказывает полноту блока.

Gate: все данные первой поставки воспроизводимы; для полной истории отдельно проверены исторические переходы и доступность входных данных.

## E07 — приёмка и первая поставка

Зависимости: E06. Стек: закреплённые сборки/образы, выбранный deployment target, native fixtures, fault injection, metrics и benchmark harness.

- [ ] E07-01 Зафиксировать hardware, нагрузку и пороги до приёмочного запуска. Готово: определены допустимые capture overhead, live lag, recovery time, disk/RAM и outage window.
- [ ] E07-02 Выполнить end-to-end native correctness и fault matrix. Готово: все обязательные проверки пройдены; отклонения не скрыты формулировкой supported.
- [ ] E07-03 Подготовить runbook запуска, остановки и диагностики ошибок доставки через логи и recovery drill по REC. UI/визуализация не входят в этап.
- [ ] E07-04 Подготовить reviewable release bundle. Готово: исходники/commit, configs, версии, результаты, ограничения, точка остановки и процедура обновления сохранены. Публикация/деплой выполняются только в разрешённом пользователем контуре.
- [ ] E07-07 Подготовить open-source поставку. Готово: LICENSE/notices, сборка, схемы сообщений, .yml, инструкции запуска и support matrix готовы. Публикация отдельно разрешается.
- [ ] E07-08 Проверить изоляцию сетевых процессов. Готово: добавление, изменение конфига, остановка и перезапуск одного экземпляра не требуют изменения/перезапуска остальных; влияние history job одной сети на live других измерено в выбранной topology. Общие инфраструктурные сбои проверяются в согласованной модели REC отдельно.

- [ ] E07-09 Принять результат в NATS на fixtures пяти сетей: типизированные поля, части, lifecycle, допустимые повторы, metadata пустых блоков и PubAck; измерить live lag. Без production verifier полноты.

Gate: отдельно приняты Ethereum, BSC, Base, Arbitrum и Polygon; первый контур готов только при выполнении согласованных критериев всех пяти. Успех одной сети не распространяется на другие.
