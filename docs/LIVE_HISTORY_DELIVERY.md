## Два независимых загрузчика

- Live — длительно работающий pod своей сети; получает новые блоки, нормализует данные, пишет в WAL и отправляет через сетевой Gateway в NATS.
- History — другой pod той же сети. Запускается по простой команде диапазона, получает блоки N…M включительно и завершает работу после подтверждения доставки подготовленных данных каждого блока. В Compose это отдельный сервис/процесс, а не режим, останавливающий live.
- History не согласует диапазон с live и не вычитает «уже обработанные» участки. Пересечения и повторные команды допустимы, повторные публикации ожидаемы.
- Каждая сеть имеет собственные загрузчики, конфигурацию, прогресс и Gateway. Общая инфраструктура NATS сохраняется. History не использует live pod как обязательный сервис дедупликации или job scheduler.
- Native clients/executors сохраняются из CLIENT_MATRIX. Отдельный pod не получает право открыть writable datadir работающего live client. Исторический state/replay обеспечивается поддержанным профилем: свой writable state или подходящий immutable snapshot/native source. Конкретные архивы и затраты проверяются в E01/E06.
- CPU/RAM/I/O лимиты history задаются отдельно. Разные pods сами по себе не гарантируют отсутствие конкуренции за диск/узел/NATS; это проверяется эксплуатационными тестами, не сканированием полноты блоков.

## Команда истории

Логический CLI-контракт: `extractor history --config <network.yml> --from N --to M`. Это проект синтаксиса, не существующая команда.

Одна команда запускает один конечный проход для выбранной сети. N и M — целые неотрицательные номера, N ≤ M; включены обе границы. Конфиг определяет сеть, native profile, источники и подключение к Gateway/NATS. Неверные параметры или недоступные native данные дают явную ошибку; диапазон не сокращается молча. Если M ещё недоступен, задание сообщает ошибку/недоступный блок; автоматическое ожидание будущего head не требуется для базовой команды.

В Kubernetes history может запускаться как отдельный Job/pod с размещением на узле ноды; локально/Compose — отдельный процесс/service на том же хосте. Это deployment упаковка, не вызов Kubernetes API из загрузчика. Точный wrapper CLI/упаковка реализуются в E06/E07. Постоянный управляющий API, scheduler, UI, dashboard и просмотр истории заданий сейчас не нужны.

Повтор команды создаёт новый run_id и может передать весь диапазон снова. Retry одного сообщения внутри запуска сохраняет его event_id, bytes и part layout. Эти два случая не смешиваются. Не вводится глобальная уникальность по block hash/tx hash для подавления повторных запусков.

D36: основной загрузчик получает только live. История — отдельный сервис на том же узле/хосте, что и native нода, запускаемый командой N–M; никакого default трёх часов или history через YAML/apply. Интерфейс единый для сетей, native реализация своя, Kubernetes API не требуется. Детали конфигурации и restart — [CONFIG_CONTRACT](CONFIG_CONTRACT.md).

## Служебные стадии блока

Ключ наблюдения: `(network_id, producer_id, run_id, block_number, block_hash)`. Один native блок может иметь несколько записей разных запусков. Hash/parent/height копируются из native источника; пересчёт хеша и независимая проверка состава в загрузчике не требуются. Данные и native validation самого клиента не отключаются.

| Стадия | Что означает | Чего она не означает |
|---|---|---|
| RECEIVED | Native источник передал блок загрузчику; зафиксированы identity и контекст получения | Все записи уже надёжно сохранены или блок доказанно полный |
| WAL_SAVED | Нормализация данного получения завершена; подготовленные immutable сообщения и закрытый список их references сохранены по выбранному durable WAL-контракту | Состав независимо сверен с блокчейном или что-либо принято NATS |
| NATS_ACKED | Gateway получил PubAck для каждого сообщения/части из закрытого списка и передал подтверждение загрузчику | Бессрочное хранение, проверка receiving side, отсутствие дублей или доказанная полнота блока |
| ERROR | Ошибка получения, нормализации, WAL или публикации с явной стадией/причиной | Успешная доставка; ошибка не продвигает delivered cursor |

Закрытый список формируется из фактически подготовленных сообщений после завершения обработки блока. Это локальный delivery batch, а не native inventory verifier. В список входит metadata блока, поэтому пустой блок тоже имеет передаваемую запись. READY/закрытие producer plan предшествуют PublishBatch; Gateway публикует только CLOSED batch. Потоковая передача означает отправку готовых данных частями с ограниченной RAM, а не публикацию незакрытого STAGING. Ошибка нормализации не становится NATS_ACKED.

При multipart publication подтверждение одной части не завершает сообщение. При потерянном PubAck/IngestAck допускается повтор: транспорт at-least-once. Проверка структуры, размеров, digest транспортных bytes и ошибок RPC остаётся необходимой для доставки и не является удалённой проверкой полноты блока.

Задание заканчивается успешно, когда для каждой запрошенной высоты выполнен проход получения и доставки её подготовленного batch. Это контроль исполнения команды N–M, не доказательство полноты транзакций/балансов. Не вводятся BlockComplete/coverage COMPLETE, проверенный диапазонный отчёт или независимый oracle в production-пути.

## Быстрое хранилище прогресса — принято D33

RocksDB каждого writable контура хранит pending messages и минимальное служебное состояние; отдельный сервер БД не нужен. [Pins](research/ROCKSDB_STACK.md) и [протокол записи/очистки](ROCKSDB_DELIVERY_PROTOCOL.md) закреплены в .06. После ACK архив статусов не сохраняется. Никаких throughput обещаний без измерений.

Adapter хранит получение, WAL references и полученный IngestAck. Gateway хранит publication mapping и PubAck отдельных частей в своём журнале сети. Это разные факты. Разные pods не открывают один embedded DB файл на запись; общая per-network identity не означает shared writable volume. Отдельная серверная БД, общий job coordinator и сервис визуализации сейчас не добавляются.

Минимальные поля: native identity/parent, producer/run/mode, стадия и время, closed batch marker, event/part references, WAL offsets, ACK/error state, cursor задания. Ключи blocks/jobs/messages служат только передаче, не запросам балансов и не дедупликации blockchain records. Состояние RECEIVED может быть наблюдаемым до durable записи; потеря такого наблюдения не должна превращаться в ложный WAL_SAVED. Атомарность, sync, cleanup markers и release определены в ROCKSDB_DELIVERY_PROTOCOL.

## Lifecycle и сообщения

Сохраняются transaction/block metadata и native reorg/finality observations. Lifecycle IDs относятся к producer/run: live/history не обязаны выдавать одну activation_id для одинакового включения. У сообщения есть native inclusion identity для принимающей стороны и отдельная delivery identity для retry. Removed/status ссылаются на свою наблюдаемую активацию; receiving-side объединение дублей/веток не проектируется.

Metadata источника, native transaction types, receipt/logs/calls/actions/state changes по принятому scope сохраняются. Исключение verifier не разрешает произвольно обрезать данные или заменить неизвестный native тип выдуманной транзакцией. Ошибка обработки — ERROR, а не успешная передача.
