# E00-07 / E00-09 — пользовательский YAML и запуск истории

2026-10-20. IN_PROGRESS; только проектирование ТЗ. Предложения ниже не являются принятыми решениями. Исходные требования: D06/D10/D12/D14/D23/D26–D33 в [DECISIONS](DECISIONS.md). Детальная wire/schema реализация и deployment не создаются.

## Уже принято

- Пользователь выбирает поддержанные сети и параметры через .yml, без изменения исходников. Новые неподдержанные native adapters одним YAML не появляются.
- Каждая сеть — независимый контур; live/history — разные pods/processes. Изменение одной сети не требует перезапуска других.
- По умолчанию начальная история за три часа, либо от явно заданного блока; далее live. Вычисленная граница сохраняется для restart с диском, не пересчитывается заново.
- Ручная history-команда задаёт включительный N–M; повтор и пересечения разрешены. При недоступных данных — ERROR, без молчаливого сокращения.
- Ранее D06 требует автоматически догружать историю после изменения стартового блока YAML. D23 требует отдельного history pod. Способ совместного выполнения этих требований ещё не выбран; ручная команда не отменяет D06.
- Pending данные RocksDB не удаляются из-за изменения YAML. ACK cleanup/recovery определены [ROCKSDB_DELIVERY_PROTOCOL](ROCKSDB_DELIVERY_PROTOCOL.md).

## Предлагаемая структура (draft)

Рекомендация: один файл на экземпляр сети, один и тот же профиль используется live и history. Набор развёрнутых сетей задаётся набором выбранных профилей; общего runtime-координатора всех сетей не требуется. Точные имена полей и схема пока не утверждены.

| Группа | Смысл | Что ещё определить |
|---|---|---|
| schema_version | Версия формата конфигурации | Правила совместимости и неизвестных полей |
| network/profile | Одна поддержанная сеть и native profile | Сопоставление ID сети и адаптера |
| history/start_block | Начало стартовой/автоматической истории | Отсутствие = default три часа; reload и направление сдвига — CFG-S03 |
| native | Параметры native источника/state/replay | Никакой замены production extraction публичным RPC |
| delivery | Endpoint Gateway, NATS для Gateway, ссылки на credentials | Разделение полей по роли; секреты не в примерах открытым текстом |
| storage | Каталог RocksDB конкретного owner | Под не должен открывать writable каталог другого процесса |
| runtime | Рабочие настройки процесса | Hot-reload vs restart — CFG-R1/CFG-S04; дисковая квота/TTL pending не вводятся |

Рекомендация валидации: до применения разобрать весь документ, проверить типы/диапазоны/profile, не применять частичный некорректный конфиг; при invalid reload продолжить с последней принятой версией и явно сообщить ошибку. Это draft, утверждение следует после выбора reload scope.

## CFG-R1 — текущие вопросы

### CFG-R1.1 — кто запускает отдельный history pod автоматически

Изменение start_block должно привести к новому history run без ручной команды, но live pod не выполняет историческую загрузку. Предложение: небольшой отдельный launcher для одной сети наблюдает применённый YAML и создаёт history Job в Kubernetes или отдельный процесс/контейнер локально. Это новый технический компонент, не уже принятое решение. Управление pods/контейнерами требует описания deployment permissions; права не выдаются live extractor автоматически.

Вопрос пользователю: допустим ли такой per-network launcher? Альтернатива — запуск средствами внешней deployment automation; она должна выполнять ту же автоматическую реакцию. Отказ от авто-догрузки и только ручная N–M команда означал бы явное изменение D06 и не предполагается.

От ответа зависит, кто читает YAML, где хранит launch intent и как выполняет bootstrap/обновления. Эти дочерние детали не выбираются в этом раунде.

### CFG-R1.2 — какие настройки менять без рестарта

Предложение: hot-reload только стартового блока истории. Смена сети/profile/native paths/Gateway-NATS connections/storage paths требует рестарта соответствующего процесса; другие сети не затрагиваются. Для production deployment применение изменённого файла и доставка его процессу должны быть отдельно описаны; файл на машине пользователя не меняет удалённый pod сам по себе.

Вопрос: достаточно ли такого минимального reload, или есть конкретные другие поля, которые обязательно менять на ходу? Детальные численные runtime настройки можно определить позднее без обещания hot-reload всех полей.

### Уже определено — конфиг и запущенная ручная команда

По протоколу .06 N–M и профиль активного history job фиксируются при старте. Изменение start_block в YAML не переписывает молча запущенную ручную команду; её продолжение после restart следует сохранённым параметрам. Pending данные при этом не теряются.

Повторного вопроса о сохранении исходного N–M нет. Поведение автоматических history jobs при последующих изменениях стартовой границы рассматривается в CFG-S03 после выбора launcher.
